# v2 운영 보호 기능과 배포 전제

이 변경은 기존 기관 서버의 보호 기능을 `chatbot` 브랜치의 v2 코드에 정식 반영합니다. 이 PR 자체로 AWS 배포·DB 변경·유료 API 호출·호출 한도 증액을 실행하지 않습니다. 기존 모델 설정, 내부 인증, 요청 본문에 묶인 실제 사용자 동의 서명, 개인별 판정 계약은 유지합니다.

## 1. 기존 호출 원장과 동의 재사용 방지

`FOOD_CHATBOT_EXTERNAL_AI_STATE_DB`는 기존 운영 SQLite 원장의 절대 경로입니다. 서비스 계정이 그 파일과 부모 디렉터리에 읽기/쓰기할 수 있어야 합니다. 원장에는 요청 본문·프로필·키 대신 호출 종류/시각과 단방향 nonce digest/만료 시각만 저장합니다.

- 기존 스키마 `budget(id, cap, prior)`, `calls(id, kind, started)`, `nonces(digest, expires)`를 그대로 사용합니다. 기존 `prior`와 호출 행을 합산하며, 시작 시 초기화·재생성·카운터 리셋·한도 변경을 하지 않습니다.
- 운영 한도는 원장 `cap`으로 결정하며 코드상 최대 허용은 기존 승인치 1,000회입니다. 생성·임베딩의 물리적인 HTTP 요청 직전에 트랜잭션으로 1회를 예약합니다. 한도 초과로 전송 자체가 막히면 외부 AI 사용 표시도 false로 유지합니다. 전송 실패·타임아웃도 환불하지 않으며, 예약 직후 프로세스 종료/취소가 일어나면 실제 전송보다 보수적으로 셀 수 있습니다. 금액 상한이나 일일 한도가 아닙니다.
- production에서 외부 AI를 켜면 정상 원장이 필수입니다. 누락·손상 시 준비 검사는 실패하고, 실제 전송도 차단됩니다. 원장 경로를 지워 제한을 우회할 수 없습니다. 개발 환경의 기존 가짜 전송 테스트는 원장 없이 실행할 수 있습니다.
- 동의 proof는 같은 원장에 원자적으로 소비하며 서버 재시작·같은 파일을 공유하는 여러 프로세스에서도 재사용을 거절합니다. 살아 있는 nonce가 10,000개면 새 proof를 거절하고 기존 proof를 밀어내지 않습니다.
- SQLite는 **단일 호스트의 로컬 영속 디스크**용입니다. 여러 EC2에서 각자 파일을 두거나 네트워크 파일시스템에 놓아 전역 제한이라고 주장하면 안 됩니다. 다중 호스트 배포에는 별도 공유 저장소 구현이 필요합니다. 기존 `FOOD_CHATBOT_SHARED_REPLAY_PROTECTION` 및 대화 신원 검증 요구를 제거하지 않습니다.

운영 백업·복귀 시 원장과 SQLite journal 파일을 일관된 방식으로 보존해야 합니다. 소스 복귀를 이유로 오래된 원장을 덮어쓰면 사용량과 nonce가 되돌아가므로 금지합니다. 원장 신규 생성 함수 `initialize`는 운영자가 실제 기존 사용량을 확인한 뒤 사용하는 별도 준비 도구이며 앱 시작에서 호출하지 않습니다.

## 2. 임베딩 실제 전송 경로

생성은 기존 urllib 전송 직전에, 임베딩은 실제 OpenAI SDK의 sync/async HTTP transport에서 예약합니다. 두 임베딩 경로 모두 같은 원장을 쓰고, 허용된 endpoint/model과 64 KiB 요청 크기를 확인합니다. 프록시 환경 상속·리다이렉트를 허용하지 않습니다.

원장이 필요한 경로는 SDK 자동 재시도 0회·연결 재시도 0회·요청 timeout 10초입니다. 향후 SDK에서 재시도해도 transport를 통과하는 각 시도를 따로 셉니다. async 요청도 차단되지 않은 별도 통로가 아니라 동일한 예산 경계입니다.

물리 요청의 문서 배치는 최대 2개입니다. 기존 RAG 조각 상한 4,000자 및 공식 발췌문 상한 3,000자를 JSON escape한 최악의 경우도 64 KiB 이내에 들어갑니다. **RAG 문서 분할 크기나 임베딩 모델은 바꾸지 않습니다.** 인덱스 재생성에서는 배치 수만큼 호출이 늘 수 있으므로 남은 횟수를 먼저 확인해야 합니다. 기존 인덱스를 이 PR 때문에 자동 재생성하지 않습니다.

## 3. 출처 미확인 상태의 명시적 운영 모드

기존 환경변수 이름을 그대로 지원합니다.

| 설정 | 역할 |
|---|---|
| `FOOD_CHATBOT_TEAM_UNVERIFIED_CATALOG=true` | 출처 목록이 비어 있는 팀 운영을 명시적으로 선택. 기본은 false |
| `FOOD_CHATBOT_PRODUCT_LABEL_ELIGIBLE_SOURCES` | 이 모드에서는 비어 있어야 함. 가짜 출처 등록 금지 |
| `FOOD_CHATBOT_ENABLE_CONVERSATIONS=false` | 이 모드는 기존처럼 서버 대화 영구 저장을 사용하지 않음 |
| `FOOD_CHATBOT_TEAM_EXTERNAL_AI=true` | 이 모드에서 외부 AI를 추가로 허용하려는 운영자 선택 |
| `FOOD_CHATBOT_ENABLE_EXTERNAL_AI=true` | 외부 처리 기능 활성화. 원장과 유효한 요청별 동의가 여전히 필요 |

일반 production 모드의 출처 검사는 그대로입니다. 미확인 모드에서도 MySQL TLS, lineage 스키마, 내부 토큰, 동의 서명, 요청 제한 등 다른 준비 검사를 통과해야 합니다. `/ready`의 `product_label_source_registry_configured`는 false를 그대로 보여주고 `team_unverified_catalog`를 별도 표시합니다.

### 응답 보존과 v2 권한 구분

- 기존 DB/rules 응답은 유용한 사실·주의 설명을 보존합니다. 출처 미확인 상품을 자유로운 LLM 문구로 섭취 가능하다고 확정하지 않습니다. 검증되지 않은 추천/레시피를 새로 허용하지 않습니다.
- **개인별 결과를 빈 배열로 바꾸지 않습니다.** 이름, 식별값, 개인별 결과와 v2 `profileKey`, `backend_analysis`, 계약/context 헤더를 유지합니다.
- v2 `product_decision`은 인증된 백엔드가 계산한 PASS/DANGER/UNKNOWN을 설명하는 경로입니다. 로컬의 예전 판단으로 다시 덮어쓰지 않고, 출처 미확인 및 실제 안전을 보증하지 않는다는 문장만 덧붙입니다. PASS와 출처 검증 완료는 같은 뜻이 아닙니다.
- 새 알레르기 조건·모호한 대상·새 상품 선택을 요구하는 v2 규칙 기반 안내도 보존합니다. 이런 응답을 일반적인 ‘상품부터 검색’ 안내로 교체하지 않습니다.
- 응답 제한은 감사 로그 기록 전에 적용합니다. 유효한 내부 토큰이나 실제 동의 없이 외부 API를 호출하게 만드는 기능은 없습니다.

## 검토 및 배포 순서

1. 챗봇 담당자가 v2 판정/개인별 응답 보존과 팀 모드 정책을 검토합니다. 기본 브랜치 main이 아니라 AI v2 개발 브랜치 chatbot을 대상으로 한 PR입니다.
2. 가짜 키·가짜 상품·임시 SQLite로 원장 동시성/실패·nonce 재사용·SDK sync/async·v2 0/1/2/21명·인증·동의 검사를 실행합니다. 실제 provider 호출은 필요하지 않습니다.
3. 병합 후 별도 배포 승인 단계에서 운영 원장 경로/권한·누적량·모델·출처 설정·RAG 인덱스 호환·Linux 실행 환경을 읽기 확인합니다. 기존 상태와 백업을 확보합니다.
4. 병합 커밋 그대로 배포하고 검증합니다. 이 PR의 로컬 검사만으로 AWS 배포 또는 실제 휴대폰/유료 생성 검증이 끝났다고 판단하지 않습니다.

## 로컬 검증 기록 (2026-11-02)

- Linux / Python 3.12.3, 외부 DNS·비루프백 socket 연결 차단, 가짜 키·임시 SQLite·memory 저장소로 검사했습니다. AWS·운영 DB·실제 유료 API 호출은 0회입니다.
- 추가 회귀 67개 전부 통과: 동시 호출 상한, 기존 사용량 보존, 실패 전송 집계, 재시작 후 nonce 재사용 거절, sync/async 실제 SDK 배치, 한도 초과 시 미사용 표시, v2 판정·헤더·개인별 결과·조건 변경 안내 및 인증 경계.
- 전체 실행은 원본 `17cb7b4` 3,005 통과/14 실패, 수정본 3,072 통과/동일 14 실패였습니다. 14개 모두 Windows 체크아웃의 레시피 자료 CRLF 변환으로 검토 해시가 달라진 사례였습니다. 테스트 사본의 해당 자료를 `git show` 원본 바이트로 복원한 후 레시피 검사 39개를 양쪽에서 재실행해 모두 통과했습니다. 최종 고유 검사 결과는 원본 3,019개/수정본 3,086개 통과이며, 전체를 두 번째로 반복 실행한 수치는 아닙니다.
- RAG 원문 자료도 정확한 Git blob 바이트가 필요합니다. 검토 자료·해시 기준을 수정하거나 검증을 우회하지 않았습니다. Linux의 정상 체크아웃 또는 `core.autocrlf=false`로 새로 받은 별도 사본에서 `python -m pytest -q tests`로 재현할 수 있습니다.
- 상한 비교를 의도적으로 `>=`에서 `>`로 바꿨을 때 경계 검사가 실패하는 것을 확인했고, 원래 바이트로 복원한 뒤 통과했습니다.
- 별도 코드 검토에서 발견한 v2 조건 변경 안내 덮어쓰기와 대량 임베딩 배치 크기 문제를 수정했습니다. 실제 앱·AWS·유료 생성 품질·운영 인덱스 호환은 배포 단계에서 별도 확인해야 합니다.
