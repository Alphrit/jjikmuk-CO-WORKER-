# 찍먹 AI — 알레르기 중심 식품 챗봇

이 디렉터리는 범용 GPT나 의료 상담 서비스가 아니라, **식품 DB의 라벨 정보와 사용자가 켠 프로필을 비교해 답하는 앱 내 챗봇**입니다.

**이전 로컬 검사 기록(2026-11-02, v2 작업 전):** 독립 검사에서 발견한 상품 대상 전환·증상 표현·초기화·비교·추천·레시피·RAG 문맥 오류를 AI 서비스 코드에서 수정했습니다. 기존 검사 기대값을 유지한 전체 pytest **2,938개 통과**(새 회귀 163개 포함), 새 대화·추천 **73/73**, 실제 OpenAI **기존 27/27·새 24/24**, 실제 RAG 문서 **40/40**, 실제 서버 **108/108**, 실제 MySQL 대화 **22/22**를 확인했습니다. 서버 저장·재시작·삭제는 임시 SQLite에서 검사했습니다. **당시 로컬 `.env`의 MySQL 서버 시작은 감사 컬럼 7개 누락으로 실패했습니다.** 이 기록은 이후 갱신된 DB나 현재 AWS 상태를 재검사한 결과가 아닙니다. 앱·백엔드 연결과 요청 제한 시간도 담당 팀원 작업으로 남아 있습니다. 프론트·백엔드·`.env`·실제 DB는 변경하지 않았습니다. 전체 테스트·재현 결과와 응답 품질의 한계는 [최신 수정·검증 기록](evaluation/2026-11-02-post-fix-audit.md)을 확인해 주세요.

## 백엔드 판정 v2 연동 (2026-11-02)

기존 요청과 `analysisContext`가 포함된 `chat-analysis-v2` 요청을 함께 지원합니다. 첨부 문서에 명시된 팀 백엔드 커밋의 실제 `ProductService`·DTO를 확인해 알레르기/식단 판정 구조를 구현했습니다. 개인 결과는 `profileKey`로 연결하며, 전체 OFF·상품 미선택·정보 부족을 구분합니다. v2 내용과 인증·확인 헤더를 검증하고 실제 처리한 응답에만 같은 contextId를 반환합니다.

일반 RAG·추천·비교·레시피·저장 대화 기능은 기존 경로를 유지합니다. v2에서 백엔드가 보낸 상품의 판정은 AI가 임의로 재판정하지 않습니다. 다른 상품을 검색하거나 채팅에서 개인 조건을 추가했다면 그 상품/조건에 맞는 새 백엔드 판정이 필요합니다. 자세한 요청/응답, 예제 JSON, 제한 및 팀 작업은 [v2 연동 문서](docs/backend-analysis-v2.md), 테스트와 실제 서버·OpenAI 확인 결과는 [v2 검증 기록](evaluation/2026-11-02-backend-v2-verification.md)에 정리했습니다.

**AWS 배포 완료를 뜻하지 않습니다.** 백엔드 담당자가 v2 호출 경로에 기존 내부 토큰·본문 동의 서명을 연결한 뒤 해당 버전과 공동 검증해야 합니다. 이번 변경은 AI 폴더에 한정하며 프론트·백엔드·`.env`·운영 DB를 수정하지 않았습니다.

## 지원 범위

- 제품 섭취 가능 여부: 원재료·알레르기 표시와 활성 프로필 비교
- 직접 알레르기 충돌과 교차오염 가능성 분리
- 여러 활성 프로필의 전체 결론 및 프로필별 결과
- 제품 원재료·알레르기 표시·영양 수치 설명
- 채식, 저당, 저염, 글루텐프리, 저칼로리, 저지방, 고단백 조건
- DB 제품 비교와 충돌 시 대체 제품 2~3개 제안
- 제품을 활용한 레시피와 알레르기 충돌 시 대체 레시피
- 여러 대화방, 자동 제목, 이름 변경, 전체 기록 다시 보기, 개별·전체 삭제
- 제품 라벨 정보 불일치 신고
- 현재 발생한 중증 알레르기 반응에 한정한 최소 응급 안내

질환별 섭취 판단, 진단·치료, 약물, 상한 음식·보관 안전, 범용 지식·시사·잡담은 지원하지 않습니다.

## 핵심 판단 원칙

1. 기존 요청에서는 서버 제품 저장소에서 제품을 식별하며 본문 제품 상세 값은 조회 힌트로 사용합니다. 인증된 v2 요청은 백엔드가 조회·판정한 현재 바코드의 상품과 개인별 판정을 설명합니다.
2. ON 상태인 모든 프로필을 적용합니다.
3. 한 명이라도 직접 알레르기 충돌이 있으면 전체 결론은 `avoid`입니다.
4. 답변에는 어떤 프로필의 어떤 성분이 충돌했는지와 프로필별 결과를 함께 제공합니다.
5. 기존 AI 판정에서는 교차오염 표시를 직접 함유와 구분해 `caution`으로 처리합니다. v2 상품 판정에서는 백엔드가 제공한 상태를 유지하며 AI 분류로 덮어쓰지 않습니다.
6. 확인된 일치 성분이 없다는 결과는 `no_known_match`이며 안전 보증이 아닙니다.
7. 기존 요청에서 새로 말한 알레르기는 그 요청에만 임시 적용합니다. v2에서는 추가 조건이 전달받은 판정에 포함되지 않았으면 조건 반영 후 재확인을 안내합니다. 계정 프로필을 채팅으로 수정하지 않습니다.
8. 누구에게 새 알레르기가 적용되는지 불분명하면 여러 프로필을 임의로 합치지 않습니다.

알레르기·채식 조건의 대상 식별은 `condition_subject.py`를 함께 사용합니다. 제품명 안의 ‘아이’·‘나’ 같은 부분 문자열을 사람 이름으로 해석하지 않습니다. OFF 프로필은 대상 언급을 식별할 때만 참조하며, 그 사람의 조건을 ON 프로필에 옮기지 않습니다. ‘새우 알레르기는 없어’라는 부정 발언으로 새 알레르기를 추가하지 않으며, 반대로 채팅 발언만으로 등록 알레르기를 삭제하지도 않습니다. ‘새우 알레르기 없는 과자 추천’처럼 제품의 제외 조건을 요청한 문장은 개인의 알레르기 부정과 구분합니다.

엄마를 OFF하고 아빠를 ON한 뒤 “엄마는 먹어도 돼?”, “그럼 엄마는?”이라고 물으면 엄마 프로필을 선택하도록 안내하고 `check_required`를 반환합니다. “그럼 먹어도 돼?”처럼 대상을 다시 지정하지 않으면 현재 ON인 프로필을 적용합니다. 근거 부족으로 최종 평가를 보류했다면 `overall_decision`과 프로필별 전체 결과도 `no_known_conflict`로 표시하지 않습니다. `allergy_status=no_known_match`는 표시 성분과의 일치 여부만 나타내며 전체 평가 완료를 의미하지 않습니다.

채식 조건 확인이 필요한 경우에도 현재 제품에서 확인된 직접 알레르기 충돌·교차오염 경고와 프로필별 결과는 유지합니다. 조건이 미정인 동안 레시피나 대체 제품을 확정하지 않으며, 확정된 제외 조건은 보존하고 미확인 항목만 질문합니다.

질문에 확실한 알레르기와 불확실한 알레르기가 함께 있으면 각각 구분합니다. 예를 들어 땅콩 알레르기는 확실하지만 우유 알레르기 유무를 모른다고 한 경우, 땅콩만 임시 적용하며 우유 조건의 확인 필요 상태를 지우지 않습니다. 확인 전 개인 적합성 판단·레시피·대체 제품 추천을 보류합니다. 불확실한 항목을 실제 알레르기로 확정하거나 계정에 저장하지 않습니다.

새 알레르기의 대상이나 유무를 확인하는 중에도 등록된 알레르기 충돌은 표시합니다. 이 경로는 현재 요청의 명확한 제품 식별자(또는 명확한 ‘이 제품’ 후속 질문의 기존 식별자)를 DB에서 다시 조회할 뿐, 이름으로 후보를 검색·선택하거나 외부 AI를 호출하지 않습니다. 새 식별자 조회 실패·식별자 불일치·확인되지 않은 제품 본문으로는 과거 제품의 경고를 새 제품의 판정처럼 표시하지 않습니다. 이때 현재 제품을 확인하지 못했다면 이전 제품 참조를 해제해 다음 ‘이 제품’ 질문에서도 과거 제품이 자동으로 되살아나지 않도록 합니다. 대화 원문·식이 목표·중복 기록은 삭제하지 않습니다.

채식 허용 여부가 미확인인 동안에도 제품의 표시 영양값·성분 확인·제품 요약에는 규칙 기반으로 답합니다. 미확인 상태는 유지하고 식이 적합성 판단은 보류하며, 다음 개인화 레시피·제품 추천 요청에서는 다시 확인합니다. 이 정보 제공 경로에서도 기존 알레르기 경고는 유지합니다.

## 식이·영양 원칙

- 알레르기 판단이 식이 조건과 비선호 성분보다 우선합니다.
- 채식은 제한 원재료를 확인하며, 유제품·달걀 허용 범위가 모호하면 채식 유형을 확인합니다.
- 밀 성분이 보이지 않는다는 이유만으로 글루텐프리라고 판정하지 않습니다.
- 저당·저염·저칼로리·저지방·고단백은 제품의 명시 표시가 있을 때만 일치로 표시합니다.
- 숫자만 있는 경우 수치와 기준량을 설명하되, 서비스 자체 임계치로 높음·낮음이나 건강 적합성을 만들지 않습니다.
- 제품 간 숫자 비교는 출처를 추적할 수 있고 영양 기준량이 같은 경우에만 수행합니다.

## 레시피와 추천

요청 제품이 활성 프로필의 알레르기와 충돌하면 해당 제품을 그대로 사용한 레시피를 제공하지 않습니다. 충돌 이유를 먼저 밝히고, DB에서 확인된 대체 제품을 제안한 뒤 그 제품을 사용한 레시피를 생성합니다. 최종 레시피 재료는 다시 알레르기와 대조합니다.

대체 제품은 모든 활성 프로필의 직접 충돌·교차오염, 식이 조건, 비선호 성분을 적용해 필터링합니다. 후보가 부족하면 실제 후보만 반환하며 제품을 생성하지 않습니다.

제품 원재료·알레르기 표시가 없으면 그 제품의 개인화 레시피를 확정하지 않습니다. LLM 초안은 제목·사용량·조리 단계·대체 재료를 검사하며, 허용 재료 밖의 복합 식품이나 근거 없는 안전·영양 인증 문구가 있으면 규칙 레시피로 돌아갑니다. 규칙 템플릿은 `app/services/recipe_templates.py`, 독립적인 초안 검사는 `recipe_validation.py`에 있습니다.

LLM 레시피는 현재 **1인분**으로 제한하며, 검토된 템플릿의 재료명·사용량 조합과 제한된 조리 어휘만 허용합니다. 새로운 안심 표현이나 재료 추가를 금지어 목록만으로 판단하지 않습니다. 허용 문법 밖의 표현은 유효한 문장이어도 규칙 레시피로 대체될 수 있습니다. 사용량 제한은 생성 오류를 막는 운영상 경계이며 영양 적합성 기준이 아닙니다. 중복 검사는 제목·분량 변경을 제외하고 재료 구성과 정규화된 조리 동작(예: 섞기/버무리기)을 사용합니다.

일반 레시피의 기존 후보 뒤에는 `app/data/reviewed_recipes/`의 원문 대조를 마친 COOKRCP01 2건을 추가했습니다. 이 경로는 **LLM 생성과 별개**이며, 원문 인분이 불명확하면 `recipe.servings`에 `원문 분량 · 인분 미확인`을 반환합니다. 인분을 추정하거나 사용량을 환산하지 않습니다. 출처는 기존 공개 `sources` 필드를 사용합니다. 특정 제품의 검색 실패나 제품용 레시피를 이 후보로 대체하지 않습니다. 지원 조건·검수 범위는 아래 3차 후속 항목을 참고하세요.

규칙 템플릿과 LLM 초안 모두 `recipe_composition.py`의 재료·조리 일관성 검사를 거칩니다. 조리 단계에 목록 밖 재료를 추가하지 않으며, 저염 공통 문구가 레몬·허브를 임의로 추가하지 않습니다. 액상 제품에 대한 썰기·부수기·볶기·굽기 지시는 제품명을 생략하거나 ‘재료’로 지칭해도 거부합니다. 목록에 있는 다른 재료를 명시한 조리는 구분하며, 이 검사는 모든 조리법의 안전성 인증을 뜻하지 않습니다.

재료 참조 검사에서는 목록에 있는 정확한 제품명·재료명을 먼저 구분합니다. ‘채소주스’·‘과일소스’라는 제품명만으로 별도의 채소·과일 추가로 판단하지 않지만, 그 밖에 실제로 추가한 목록 밖 재료는 계속 차단합니다.

비교 제품명이 모호하면 제품마다 후보를 선택합니다. `conversation_state`의 비교 식별자는 매 요청 DB에서 다시 조회하며 제품 사실 자체를 신뢰하지 않습니다. `comparison_products` 응답에는 확인된 각 제품의 영양값과 기준량이 포함됩니다. 비교 기준 미선택과 제품 수치 누락은 구분합니다.

비교 중에는 “나트륨”, “그럼 단백질은?”처럼 짧게 답하거나 “첫 번째, 나트륨으로 비교해줘”처럼 선택과 기준을 함께 보낼 수 있습니다. 후보끼리 비교하라는 문장은 특정 후보 선택으로 간주하지 않습니다.

“나트륨이요”, “단백질로 부탁해”도 비교 기준으로 연결합니다. “단백질과 나트륨을 둘 다 비교해줘”처럼 여러 영양소를 지정하면 각 기준을 따로 비교하고, 일부 수치가 없으면 해당 기준의 누락을 안내합니다. “새우깡은 빼고 서울우유와 비교해줘”처럼 교체할 대상이 명확하면 해당 제품만 교체하고 새 후보를 확인합니다. 대상이 불명확하면 다시 묻습니다. 새 검색이 실패한 경우 과거 비교 결과로 복귀하지 않습니다. `conversation_state.comparison_status`는 `active`, `pending`, `unresolved`, `cleared` 중 하나이며, 새 상태는 비교 대상·검색어 전체를 교체합니다. 무상태 클라이언트는 초기화를 나타내는 빈 배열도 보존해야 합니다.

다른 제품·작업으로 전환하면 현재 비교 문맥은 `cleared`로 초기화합니다. 이전 비교 메시지 자체는 삭제하지 않습니다. 새 제품의 ‘그럼 단백질은?’을 과거 제품 비교로 바꾸지 않으며, ‘비교는 그만하고 저염 레시피 추천해줘’는 비교 종료와 새 요청을 구분해 처리합니다.

## LLM 사용 경계

판정은 규칙과 제품 DB가 담당합니다. OpenAI 모델은 다음에만 보조적으로 사용됩니다.

- 승인된 RAG 검색 근거로 일반 식품 설명을 생성하고 문장별 근거 검토
- 검증 가능한 재료 범위 안에서 레시피 문장 구성
- 규칙만으로 모호한 식품 질문의 제한적 의도 분류

LLM 출력은 제품명·원재료·알레르기·영양 수치·판정 결론을 새로 만들거나 바꿀 수 없습니다. 검증에 실패하면 규칙 응답으로 돌아갑니다. 공급자는 OpenAI 하나만 지원하며 Responses API 요청에는 `store: false`를 사용합니다.

외부 AI는 운영 스위치와 요청별 서명된 동의가 모두 유효할 때만 호출됩니다. 동의가 없거나 OpenAI가 실패해도 핵심 규칙 경로는 동작합니다.

### 현재 모델 설정

답변 생성·근거 검토·제한적 의도 분류·레시피 초안의 기본 모델은 `gpt-6-sol`, RAG 임베딩은 `text-embedding-3-large`입니다. 로컬 설정과 배포 예제의 생성 모델을 동일하게 맞췄습니다. 모델 사양은 [GPT-6 Sol](https://developers.openai.com/api/docs/models/gpt-6-sol), [text-embedding-3-large](https://developers.openai.com/api/docs/models/text-embedding-3-large) 공식 문서를 참고하세요.

```dotenv
OPENAI_MODEL=gpt-6-sol
EMBEDDING_MODEL=text-embedding-3-large
LLM_REASONING_EFFORT=high
LLM_MAX_OUTPUT_TOKENS=8192
LLM_TIMEOUT_SECONDS=120
```

GPT-6 요청은 `reasoning.effort`를 사용하고 호환되지 않는 `temperature`를 보내지 않습니다. 출력 토큰 한도에는 추론 토큰도 포함되며, 완료되지 않은 응답은 채택하지 않고 기존 대체 응답으로 처리합니다. 생성·검토에는 기존 모델보다 비용과 시간이 더 들 수 있습니다. 일반 설명의 생성 모드는 답변 생성과 근거 검토를 각각 호출하므로, 배포 시 백엔드·게이트웨이의 전체 요청 제한 시간도 확인해야 합니다.

RAG 임베딩은 축소하지 않은 3,072차원을 사용합니다. 기존 `text-embedding-3-small` 인덱스와 호환되지 않으므로 모델을 변경한 서버에서 다음 명령으로 인덱스를 재생성합니다. 승인된 설명·내부 정책 문서의 외부 임베딩 요청과 비용이 발생합니다. API 키는 서버 환경변수 또는 Git에서 제외된 `AI/.env`에만 설정합니다.

```bash
# AI/에서 실행
python evaluation/rebuild_rag_index.py
```

모델 설정만으로 외부 AI 동의나 생성 모드가 켜지지는 않습니다. 검색 근거를 활용한 일반 설명 생성에는 기존처럼 `FOOD_CHATBOT_ENABLE_EXTERNAL_AI=true`와 백엔드의 요청별 서명이 필요합니다. 앱이 동의를 묻지 않으므로 서명된 요청은 기본적으로 동의한 것으로 처리합니다(`FOOD_CHATBOT_EXTERNAL_AI_ASSUME_CONSENT=false`로 되돌릴 수 있음). `.env.example`의 응답 모드는 `generated`입니다. 설정이 없으면 코드 기본값 `extractive`로 동작해 검색한 승인 설명을 그대로 제공하므로, 배포 서버에 이 값을 꼭 넣어 주세요.

레시피 초안은 [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)를 사용해 JSON 필드·자료형, `servings: "1인분"`, 선택 제품명을 제한합니다. 형식이 맞아도 재료·사용량·조리 문장·알레르기·식이 조건 검증을 모두 통과해야 채택하며, 실패하면 규칙 레시피로 대체합니다.

## 대화 저장

- 대화방 원문은 사용자가 삭제할 때까지 보관합니다.
- 대화방 생성 시 첫 질문을 바탕으로 제목이 자동 생성되며 사용자가 변경할 수 있습니다.
- 대화방 소유자는 로그인 사용자의 서명된 ID로만 결정합니다.
- 다른 사용자의 방 조회·수정·삭제는 허용하지 않습니다.
- 같은 `turn_id` 재시도는 같은 요청일 때만 멱등 처리합니다.
- 작성 중인 입력 초안은 서버 건강 데이터로 저장하지 않고 클라이언트 로컬 상태로 처리하는 것을 권장합니다.

최근 대화 원문이 문맥 한도를 넘어도 레시피 요청 식이 조건·기준 제품과 확인된 채식 허용 범위는 별도 상태로 유지합니다. 저장된 프로필 조건은 매 요청 다시 읽으며, 질문에서 임시로 말한 알레르기를 이 상태에 영구 저장하지 않습니다. 채식 허용 범위도 계정 프로필 수정이 아닙니다. 무상태 연동은 응답의 `conversation_state`를 다음 요청에 전달해야 합니다.

채식 허용은 명확한 진술만 반영하며, “먹는 게 안 돼”, “이제 빼줘”는 금지·철회로 처리합니다. 불분명한 표현은 확인 질문으로 전환합니다. 현재 프로필의 `vegetarian_dairy_allowed=false` / `vegetarian_egg_allowed=false`를 과거 대화 허용으로 완화하지 않습니다. 선택 프로필의 채식 조건이 변경되면 저장된 허용도 다시 확인합니다. 대화 상태의 `profile_signature`는 해당 조건 변경을 감지하는 해시이며 계정 수정 권한이나 인증 서명이 아닙니다. 이 선택적 프로필 값은 저장형 요청 재검증과 멱등성 비교에서도 유지됩니다.

`vegetarian_allowances`는 유제품·달걀별 변경 감지 값(`dairy_profile_signature`, `egg_profile_signature`)과 미확인 상태(`dairy_pending`, `egg_pending`)를 선택적으로 보관합니다. 확인 질문과 재조회·다음 요청을 거쳐도 명확한 제외 조건은 유지됩니다. 다른 항목이나 저칼로리 같은 식이 목표 변경으로 제외를 해제하지 않으며, 해당 프로필 항목의 명시적인 변경은 그 항목의 미확인 상태를 해소할 수 있습니다. 이전 통합 `profile_signature` 형식도 읽되, 변경 원인을 구분할 수 없으면 과거 허용만 보수적으로 재확인하고 명시적인 제외는 유지합니다. 이 값들은 계정 권한이나 인증 정보가 아닙니다.

`dairy`·`egg`에는 사용자가 대화에서 명확히 말한 허용·제외 값을 기록합니다. 프로필의 제한과 합쳐 계산한 최종값을 사용자 발언으로 저장하지 않습니다. 예를 들어 프로필에서 유제품을 금지한 동안 “유제품은 먹어”라고 해도 현재 응답에서는 금지를 우선하되, 이를 대화의 `dairy=false`로 바꾸지 않습니다. 이후 프로필이 허용으로 변경되면 가짜 제외 조건이 남지 않습니다. 실제로 “유제품은 빼줘”라고 한 제외 조건은 유지합니다. 과거 버전이 저장한 `false`는 발언 출처를 복원할 수 없어 일괄 해제하지 않으며, 사용자의 명확한 재진술이나 현재 프로필 조건을 확인해 처리합니다.

제품 후보 선택을 거쳐도 레시피 조건과 중복 기록은 유지합니다. 조건 없는 새 레시피 요청은 이전 메시지의 식이 목표를 초기화하며, `recipe_goals_initialized`가 있는 상태에서는 과거 대화에서 해제한 목표를 다시 복원하지 않습니다. 가입 프로필의 식이 조건은 이 초기화로 삭제되지 않습니다.

대화 저장소 구현은 `app/infrastructure/conversation_storage/`의 공통 계약·메모리·SQLite·MySQL로 분리되어 있습니다. 기존 `conversations.py` import는 유지합니다. 만료일 기반 조회 제외와 자동 삭제는 제거했고, 예전 `purge_expired()` 호출은 삭제 없이 0을 반환합니다. `expires_at` 컬럼은 기존 DB 호환용으로만 남겨두며 새 쓰기는 NULL입니다. 기존 날짜 정리는 `20260910_conversation_no_expiry.sql` 마이그레이션을 사용하고 컬럼을 임의 삭제하지 마세요.

제품·활동 저장소도 `app/infrastructure/product_storage/`, `activity_storage/`의 공통 계약·메모리·SQLite·MySQL 구현으로 분리했습니다. `repository.py`는 기존 import를 유지하는 호환 진입점이며, 세 종류 저장소가 사용하는 MySQL 연결 풀·TLS·타임아웃은 `mysql_support.py`를 공유합니다. 분리를 위해 SQL이나 검색·판정 기준을 변경하지 않았습니다.

API의 사용하지 않는 보존기간 전달 코드는 제거했습니다. 신규 SQLite 대화 저장소는 만료 인덱스를 생성하지 않습니다. 기존 DB의 컬럼·인덱스·대화 원문은 자동 삭제하지 않습니다. 레거시 `histories` 활동 쓰기는 기본 비활성화를 유지하고, 배포된 DB 호환 코드와 SQL 마이그레이션은 보존합니다.

## 공개 API

- `GET /` — 실행 확인
- `GET /health` — 프로세스 상태
- `GET /ready` — DB·정책·보안 설정 준비 상태
- `POST /chat` — 채팅. `conversation_id`와 `turn_id`가 있으면 해당 방에 저장
- `POST /conversations` — 대화방 생성
- `GET /conversations` — 내 대화방 목록
- `DELETE /conversations` — 내 대화방 전체 삭제
- `GET /conversations/{conversation_id}` — 메시지를 포함한 대화방 조회
- `PATCH /conversations/{conversation_id}` — 제목 변경
- `DELETE /conversations/{conversation_id}` — 대화방 삭제
- `POST /products/{barcode}/report` — 제품 라벨 불일치 유형 신고

정확한 요청·응답 스키마는 실행 중인 `/docs` 또는 `/openapi.json`을 기준으로 합니다. 관리자 진단, 일반 피드백, 답변 재검토, 안전검토 큐 API는 제공하지 않습니다.

팀원용 요청 예시·응답 필드·인증 및 동의 서명 규격은 [API 연동 계약](#api-연동-계약)에 정리했습니다.

HTTP 응답은 `app/api/response_contract.py`의 허용 필드만 공개합니다. `/chat`과 대화방 메시지 재조회 모두 `pipeline_stage`, `fallback_reason`, `validation_failure_types`, `critical_safety_violation`, `blocked_llm_output_stored`, `source_details`, `policy_version`, `applied_rule_ids`, `evidence`, `provenance_status`를 반환하지 않습니다. 내부 `ChatResponse`와 서버 스냅샷의 진단 정보는 유지하며, UI는 `overall_decision`, 프로필별 결과, `assessment_summary`, `missing_information`을 사용합니다. 요약 범위에 `recipe`와 `comparison`이 추가됐습니다. 이는 식품 성분 대조 범위이며 의학적 안전 보증이 아닙니다.

API 안정성 평가도 같은 허용 필드를 사용합니다. 비공개인 `pipeline_stage`를 요구하지 않고, 허용 목록에 없는 진단 필드가 HTTP 응답에 노출되면 실패로 처리합니다. 실제 LLM/RAG 평가 요약에서도 공개되지 않는 `pipeline_stage`를 읽지 않습니다.

## 로컬 실행

Python 3.11 이상을 사용합니다. 현재 검증 환경은 macOS / Python 3.13.5입니다. 실행 패키지와 개발·테스트 패키지는 별도 설치 목록으로 관리합니다.

```bash
cd AI
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
uvicorn app.api.main:app --reload
```

간단한 로컬 확인에는 `FOOD_CHATBOT_DB_PROVIDER=memory`를 사용할 수 있습니다. SQLite를 사용할 때는 `FOOD_CHATBOT_DB_PATH`가 필요합니다. 운영 환경은 MySQL과 TLS가 필수입니다.

`requirements.txt` 하나에 직접 의존성과 실행용 하위 의존성의 버전을 관리합니다. 별도의 `constraints.txt` 없이 이 파일만으로 설치할 수 있습니다. `requirements-dev.txt`는 실행 목록을 포함하고 테스트 전용 `pytest`, `iniconfig`, `pluggy`를 추가합니다. 전체 개발 환경의 `pip freeze` 결과로 덮어쓰지 마세요. 현재 사용하지 않는 `langchain`, `langchain-community`, `langgraph` 계열은 제외하고, RAG에 필요한 Chroma·OpenAI SDK 등의 하위 의존성은 유지했습니다. 기존 패키지는 업그레이드하지 않았으며 PDF 원문 추출용 `pypdf==6.19.0`만 추가했습니다.

## 인증 경계

`FOOD_CHATBOT_API_TOKEN`이 설정되면 보호 경로는 `X-Food-Chatbot-Token` 또는 Bearer 토큰을 요구합니다.

저장 대화와 라벨 신고는 로그인 사용자를 신뢰할 수 있는 백엔드가 다음 헤더로 전달해야 합니다.

- `X-Food-Chatbot-User-Id`
- `X-Food-Chatbot-Identity-Timestamp`
- `X-Food-Chatbot-Identity-Nonce`
- `X-Food-Chatbot-Identity-Signature`

서명은 HTTP 메서드, 경로, 사용자 ID, nonce, 요청 본문의 SHA-256과 용도 문자열을 묶습니다. 브라우저가 이 헤더를 직접 만들게 하지 말고 인증 백엔드가 기존 값을 제거한 뒤 다시 서명해야 합니다. 여러 워커·인스턴스에서는 gateway 또는 Redis 같은 공유 nonce 저장소가 필요합니다.

외부 AI 사용 동의는 사용자 ID 서명과 별도의 secret 및 헤더 세트를 사용합니다. 본문의 boolean 값만으로 동의가 부여되지 않습니다.

실제 요청 검증에서 `영국 알레르기 혼입 표시`의 국가명이나 `제조시설의 알레르기 혼입 확률`의 시설명을 개인의 알레르기 이름으로 오인하는 문제도 수정했습니다. 혼입·교차접촉의 정보 요청을 개인 조건 진술과 구분하되, 같은 문장에 명시한 미지원 식품의 알레르기는 계속 확인 대상으로 남깁니다. 기본 추출 응답 모드에서는 지원하지 않는 주제를 임베딩 검색에 전송하기 전에 자료 부족으로 안내합니다.

`RAG_GENERAL_RESPONSE_MODE=generated`를 선택하면 같은 승인 주제·근거 범위 안에서 질문에 맞는 짧은 설명을 생성하고, 별도 LLM 호출로 문장별 근거를 검토합니다(답변 생성·검토에 최대 2회 호출하며, 필요한 경우 의도 분류 호출은 별도). 서버는 답변의 모든 문장이 검토 결과에 그대로 들어 있는지, 각 문장의 근거 인용이 현재 승인 본문의 완전한 문장인지, 복수 주제의 근거가 모두 남아 있는지 확인합니다. 명시적인 부정문을 반대로 바꾼 경우도 별도로 차단합니다. 생성·검토 실패, 모순 또는 근거 부족이면 출처가 있는 승인 본문으로 돌아가며, 검토 중 승인이 바뀌면 해당 출처를 반환하지 않습니다. 지원하지 않는 세부 질문은 두 모드 모두 임베딩 검색 전에 보류합니다.

문장의 의미가 근거에서 뒷받침되는지는 모델 검토를 포함하므로 정확도를 보장하는 장치는 아닙니다. `extractive`는 승인 본문 그대로 제공하며 기본값으로 유지됩니다. 실제 `.env`에서 `generated`를 선택하더라도 외부 AI 허용과 백엔드가 서명한 요청별 동의가 모두 있어야 검색·생성이 실행됩니다. 로컬 미리보기는 생성 답변을 거절하고 본문으로 돌아간 경우를 LLM 답변 채택으로 표시하지 않습니다.

일반 설명의 후속 질문은 최근 사용자 질문에서 주제를 이어 검색합니다. 예를 들어 무당·무가당 차이를 설명한 뒤의 “그럼 칼로리는?”은 해당 표시와 열량의 관계를 검색하고, “더 쉽게 설명해줘”는 같은 주제를 유지합니다. 어시스턴트 답변은 상품을 선택하는 근거로 사용하지 않으며, 상품명 언급이 없는 일반 질문을 상품 검색 결과로 복원하지 않습니다. “슈가프리”, “제조시설이 같다는 건” 같은 표현도 기존 승인 주제로 연결합니다. 개인 섭취 적합성, 의료 질문, 새 상품·레시피 요청은 일반 설명으로 바꾸지 않습니다.

오프라인 회귀 검증은 `python -m pytest tests/test_rag_conversation_regressions.py tests/test_rag_generated_grounding.py -q`로 실행합니다. 실제 API 연결·검색·생성 확인 결과는 [2026-11-01 외부 API·RAG 실제 호출 확인](#2026-11-01-외부-apirag-실제-호출-확인)에 정리했습니다. 모의 테스트나 소규모 실제 호출의 통과를 실서비스 전반의 정확도로 해석하지 않습니다.

### Android·백엔드 로컬 연결

**연동 작업용 계약입니다.** 2026-11-01 현재 체크아웃의 프론트 채팅은 임시 응답을 사용하고, 백엔드는 다중 프로필·동의 서명·대화 상태 중계가 완성되지 않았습니다. 아래 설정 명령만 실행해 앱 연결이 완료되지는 않습니다. 실제 구현은 프론트·백엔드 담당자가 아래 API 계약에 맞춰 진행해야 합니다.

`AI/.env`에 기존 `OPENAI_API_KEY`를 설정한 상태에서 다음 명령을 실행하면 두 서버에 동일한 별도 동의 서명 키와 외부 AI 사용 설정을 적용합니다. API 키는 AI 서버에만 남으며 출력하지 않습니다.

```sh
python -m evaluation.configure_chat_bridge --enable-external --response-mode generated
```

AI의 `.env`와 백엔드의 Git 제외 파일 `.chat-ai.properties`를 설정하는 도구이므로 백엔드 담당자와 함께 사용합니다. 백엔드에서 이 설정을 읽고 서명을 전달하는 구현도 필요합니다. 외부 AI를 끄려면 `--enable-external` 없이 실행합니다. 앱은 동의하지 않은 상태를 기본값으로 두고, 로그인한 사용자가 명시적으로 동의한 요청만 검색·생성을 허용해야 합니다. 서명은 실제 전송 본문·사용자 ID·경로·시각·nonce에 묶여 Python에서 검증됩니다. 이는 운영 배포 설정을 대신하지 않습니다.

대화 상태는 앱 요청의 `conversationState` → AI 요청의 `conversation_state`로 중계하고, 응답 상태를 다음 요청에 다시 사용하도록 연결해야 합니다. 상품 선택 후 원래 질문 이어가기와 `recipe`의 재료·분량·조리 순서·주의사항 표시도 앱에서 구현해야 합니다. 로그인 변경 시 상태와 동의를 초기화합니다.

검증 도구 `evaluation/verify_llm_rag.py`는 가상 프로필·메모리 DB의 `/chat` 요청에서 실제 임베딩 검색, 예상 문서 인용, 승인 본문과의 일치, 질문별 필수 수치·단위·조건을 확인합니다. 결과는 `evaluation/results/grounded_rag_api_verification.json`에 저장합니다. 이는 운영 서버의 DB·앱 연동 검증과 별개이며, 테스트를 위해 프로세스 안에서 허용한 설정은 실제 `.env`를 변경하지 않습니다. 운영 RAG 사용에는 외부 AI 허용과 요청별 동의 설정이 여전히 필요합니다.

영양표시 PDF 2종만 반영했던 단계의 검증은 `tests/` 1,893개, `/chat` 21/21 통과였습니다. 추가 알레르기 자료 검증은 아래 결과에 별도로 기록합니다. 실제 기본 설정의 외부 AI 허용과 서명된 요청별 동의 설정은 변경하지 않으므로 로컬 검증을 운영 앱의 활성화 완료로 해석하지 않습니다.

2026-10-15 알레르기 PDF 2종 반영 후 검증: `tests/` **1,921개 통과**, 실제 임베딩과 가상 프로필·메모리 DB의 `/chat` **30/30 통과**(재시도 0회), 답변 문장 생성 호출 0회. 인용 페이지·답변과 승인 본문의 일치·여러 주제의 근거 충족·법적 의무 및 혼입 확률 질문의 보류·개인 알레르기 오인 방지를 확인했습니다. 로컬 인덱스는 문서 24개(공식 설명 19개·내부 MD 5개), 청크 28개로 최신·검색 준비 상태입니다. 실제 운영 DB·배포 서버·Android 앱의 종단 간 검증은 이 결과에 포함하지 않습니다.

`app/knowledge/`의 MD는 이 서비스 범위의 내부 규칙 문서입니다. 공식 외부 근거는 별도로 승인한 `.source.json` 형식으로 읽으며 출처·원문 위치를 유지합니다. PDF는 실제 페이지, 웹 문서는 본문 절 제목을 사용합니다. 내려받은 PDF·CSV 원본은 `app/knowledge/raw/`에 둡니다. `raw/`는 RAG 순회에서 제외하므로 원본을 넣기만 해서는 챗봇의 지식이나 레시피가 바뀌지 않습니다. 승인 자료를 포함한 지식 문서가 바뀌면, 외부 임베딩 호출을 허용한 환경에서 인덱스를 다시 만들어야 합니다. `evaluation/` 없이도 실행할 수 있습니다.

```bash
python -c "from app.infrastructure.rag import rebuild_rag_index; rebuild_rag_index()"
```

외부 AI가 켜져 있으면(`FOOD_CHATBOT_ENABLE_EXTERNAL_AI=true`와 OpenAI 키) 일반 서버 시작(`uvicorn`)에서도 인덱스가 없거나 오래됐을 때 백그라운드에서 다시 만듭니다. 만드는 동안 요청은 받되 RAG 검색은 쉬고, 끝나면 바로 사용합니다. 끄려면 `FOOD_CHATBOT_RAG_AUTO_REBUILD=false`로 둡니다. `app/chroma_db/`의 로컬 인덱스는 Git 배포물에 포함되지 않습니다. 새 배포 환경에서는 식품 범위 지식 문서와 설정을 먼저 배치하고 위 명령으로 인덱스를 만든 뒤, 아래 준비 상태 확인이 통과해야 RAG를 활성화합니다. 문서 해시나 설정이 달라 오래된 인덱스로 판정되면 검색은 중단되며, 규칙 기반 알레르기 판정은 계속 동작합니다.

```bash
python -c "from app.infrastructure.rag import get_rag_status; s = get_rag_status(); assert s['retriever_ready'] and not s['index_stale'], s"
```

인덱스 생성도 외부 OpenAI 임베딩을 사용할 수 있으므로 운영 환경의 개인정보·네트워크 정책을 적용해야 합니다. 임베딩 호출이 허용되지 않는 환경에서는 인덱스를 자동 재구축하지 말고, 준비 상태가 확인된 인덱스를 별도 배포하거나 RAG 없이 규칙 기반 경로로 운영하세요.

RAG를 사용하는 배포에서는 다음 진입점으로 준비 검사와 서버 실행을 묶을 수 있습니다. 최신 인덱스는 재사용하고, 없거나 오래된 인덱스는 명시적으로 허용한 경우에만 재구축합니다. 준비 검사 실패 시 서버를 시작하지 않습니다. 실제 배포 설정에서 이 명령을 사용해야 하며 기존 `uvicorn` 실행을 자동으로 바꾸지는 않습니다.

```bash
python -m app.start --rebuild-rag --host 0.0.0.0 --port 8000
```

외부 임베딩 재구축을 허용하지 않으면 `--rebuild-rag`를 빼서 사전 배포된 인덱스만 검사합니다. RAG 없이 규칙 경로로 실행하려는 환경은 기존 `uvicorn app.api.main:app` 명령을 사용합니다.

### PDF·CSV 원문 준비 — 오프라인, 실제 답변 연결 전 단계

사용자가 MD를 직접 옮겨 적을 필요 없이 아래 명령으로 원본을 자동 추출할 수 있습니다. 명령은 `AI/`에서 실행합니다. PDF 파서는 `requirements.txt` 설치에 포함됩니다.

```bash
python -m app.knowledge_import prepare
python -m app.knowledge_import status
python -m app.knowledge_import search --kind pdf --query "알레르기" --limit 2
```

## API 연동 계약

이 절은 현재 AI 서버의 실제 HTTP 계약입니다. 호출 흐름은 **앱 → 인증 백엔드 → AI 서버**이며, 아래 본문은 백엔드가 AI 서버에 보내는 형식입니다. AI 서비스 토큰·서명 키·OpenAI 키는 앱에 넣지 않습니다. 백엔드는 로그인 사용자를 검증하고 해당 사용자 소유의 선택 프로필을 조회해 전달합니다.

현재 저장소의 백엔드 `POST /api/chat`는 단일 프로필·상품·메시지·대화 이력을 전달합니다. 아래 다중 프로필·대화 상태·서명 헤더·대화방·신고의 중계는 별도 연동이 필요합니다. 앞선 로컬 연결 설명을 현재 앱의 연동 완료 상태로 해석하지 마세요. 앱용 중계 주소는 백엔드 담당자와 확정합니다.

### 1. 주소와 엔드포인트

- AI 서버 로컬 주소: `http://localhost:8000` — 실제 배포 주소는 서버 설정에 따릅니다.
- 요청 본문: `Content-Type: application/json`, UTF-8. 응답은 JSON 객체이며 `data` 래퍼가 없습니다.
- 전체 필드·타입·기본값: `GET /docs`, `GET /openapi.json`.

| 메서드·경로 | 용도 | 요청 본문 / 쿼리 | 성공 응답 |
| --- | --- | --- | --- |
| `GET /` | 실행 확인 | 없음 | `200` 상태 객체 |
| `GET /health` | 프로세스 상태 | 없음 | `200` 상태 객체 |
| `GET /ready` | DB·정책·보안 준비 확인 | 없음 | 준비 시 `200`, 미준비 시 `503`; 준비 상태 객체 |
| `POST /chat` | 판정·검색·비교·추천·레시피·일반 설명 | 아래 채팅 요청 | `200` 채팅 응답 |
| `POST /conversations` | 대화방 생성 | `conversation_id: UUID`, 선택 `title: string` | `201` 대화방 요약 |
| `GET /conversations` | 내 대화방 목록 | 선택 `limit`(기본 20), `before` | `200` `{conversations: [...], next_cursor: string 또는 null}` |
| `GET /conversations/{conversation_id}` | 방·메시지 조회 | 선택 `message_limit`(기본 50, 1~100), `before` | `200` `{conversation: {...}, messages: [...], next_cursor: string 또는 null}` |
| `PATCH /conversations/{conversation_id}` | 제목 변경 | `title: string`(1~32자) | `200` 대화방 요약 |
| `DELETE /conversations/{conversation_id}` | 방 삭제 | 없음 | `204`, 본문 없음 |
| `DELETE /conversations` | 내 방 전체 삭제 | 없음 | `200` `{deleted: number}` |
| `POST /products/{barcode}/report` | 표시 불일치 신고 | `field: string` | `202` `{accepted: true, barcode: string, field: string}` |

대화방 요약은 `conversation_id`, `title`, `title_manually_set`, `revision`, `created_at`, `updated_at`, `expires_at`을 포함합니다. 목록의 `next_cursor`를 다음 요청의 `before`에 그대로 전달하며, `null`이면 마지막 페이지입니다. 메시지는 `message_id`, `sequence`, `role`, `content`, `turn_id`, `created_at`, `response`를 포함합니다. 어시스턴트 메시지의 `response`로 상품·레시피·출처 등 구조화된 결과를 복원합니다.

신고 `field` 허용값은 `product_name`, `ingredients`, `allergens`, `nutrition`, `other_label_information`입니다. 자유 입력 본문이나 일반 답변 피드백은 받지 않습니다.

### 2. 채팅 요청 — 클라이언트가 문맥을 전달하는 방식

`POST /chat` 예시입니다. 아래 바코드와 프로필은 형식 설명용이며 실제 상품·계정 데이터로 바꿔 전달합니다.

```json
{
  "message": "이 제품 먹어도 돼?",
  "barcode": "8800000000000",
  "profiles": [
    {
      "profile_id": 1,
      "profile_name": "나",
      "user_id": 42,
      "is_active": true,
      "allergies": ["우유"],
      "special_diets": ["저당식"],
      "disliked_ingredients": []
    },
    {
      "profile_id": 2,
      "profile_name": "가족",
      "user_id": 42,
      "is_active": true,
      "allergies": ["새우"],
      "special_diets": [],
      "disliked_ingredients": []
    }
  ],
  "chat_history": [],
  "conversation_state": {}
}
```

| 필드 | 전달 규칙 |
| --- | --- |
| `message` | 필수, 최대 4,000자. 후보 선택·후속 질문도 이 필드로 전송 |
| `profiles` / `profile` | 다중 / 단일 프로필 입력. 기본 연동은 `profiles` 사용. 프로필 입력 합계 최대 20개, ON인 프로필만 판정에 적용 |
| 프로필의 `allergies` | 확인된 알레르기가 없으면 `[]`를 명시. 누락은 알레르기 없음과 다름 |
| 프로필의 식이·제외 조건 | `special_diets`, `disliked_ingredients`는 문자열 배열. 채식 허용 범위가 확인되면 `vegetarian_dairy_allowed`, `vegetarian_egg_allowed`에 boolean 전달 가능 |
| `barcode` / `report_number` | 상품 식별 시 전달. 일반 설명·일반 레시피는 생략 가능. 상품명으로도 `message`에서 검색하지만 모호하면 후보 확인 |
| `chat_history` | 이전 성공 대화의 `{role: "user" 또는 "assistant", content: string}` 배열. 역할은 번갈아 배치. 최대 50개, 각 4,000자·합계 20,000자 |
| `conversation_state` | 첫 요청은 `{}`. 이후 **직전 응답 값을 통째로 전달**. 빈 배열·초기화 값도 보존 |

후속 질문은 새 `message`와 최신 선택 프로필, 이전 대화·상태를 보냅니다. 상품 후보가 나오면 상태를 유지한 채 `message: "첫 번째"`처럼 선택합니다. 단일 후보 선택 전용 API는 없습니다. `product`, `raw_product`, `raw_profile`, `raw_profiles`는 기존 입력 호환용이며, 상품 본문만으로 DB 확인을 대체하지 않습니다.

상태의 `pending_target_product`는 대상 프로필 확인을 기다리는 상품 식별자이며, 선택 후 DB에서 재조회합니다. `recipe_receipt`는 이전에 서버가 제공한 레시피를 검증하여 다시 표시하기 위한 선택 필드입니다. 클라이언트는 값을 해석·수정하지 말고 상태와 함께 그대로 전달합니다. 프로필·조건 변경, 서명 불일치, 새 레시피 요청 실패 시 과거 결과를 현재 결과로 재사용하지 않습니다. 여러 서버 또는 재시작 후 복원에는 기존 동의 서명 키(또는 서비스 토큰)가 동일하게 유지되어야 하며, 두 값 모두 없는 개발 환경에서는 같은 프로세스 안에서만 복원됩니다. 큰 상태에서는 이 선택 필드를 생략하고 재요청을 안내할 수 있습니다.

### 3. 채팅 응답과 화면 연결

다음은 주요 필드만 발췌한 형식 예시입니다. 문구·결과·배열 내용은 실제 요청과 조회 결과에 따라 달라집니다.

```json
{
  "intent": "missing_product",
  "answer": "제품 표시 정보를 확인하지 못해 판단을 보류했어요.",
  "answer_source": "rules",
  "risk_level": "unknown",
  "overall_decision": "check_required",
  "allergy_status": "unknown",
  "diet_match": "unknown",
  "preference_match": "unknown",
  "assessment_status": "incomplete",
  "missing_information": ["원재료·알레르기 표시 확인 필요"],
  "per_profile_results": [],
  "product_candidates": [],
  "recommended_products": [],
  "comparison_products": [],
  "recipe": null,
  "sources": [],
  "conversation_state": {},
  "external_ai_processing": {
    "allowed_for_request": false,
    "used": false,
    "status": "consent_not_verified",
    "services": []
  }
}
```

| 필드 | 프론트 처리 |
| --- | --- |
| `answer` | 답변 본문. HTTP 오류와 구분해서 표시 |
| `overall_decision` | `avoid` 피해야 함 / `caution` 주의 / `check_required` 추가 확인 / `no_known_conflict` 표시상 확인된 충돌 없음 |
| `allergy_status` | `conflict` 직접 충돌 / `cross_contact` 교차접촉 / `no_known_match` 표시상 일치 없음 / `unknown` 미확인 |
| `diet_match`, `preference_match` | 식이: `match`, `caution`, `not_match`, `unknown`. 비선호: `matched`, `disliked_found`, `unknown`. 알레르기와 별도로 표시 |
| `assessment_status`, `missing_information` | `complete`, `incomplete`, `unsupported` 및 부족한 정보. 미확인을 안전으로 표시하지 않음 |
| `per_profile_results` | 프로필별 ID·이름·판정·답변·이유. 배열이 비어 있으면 임의로 프로필별 결과를 생성하지 않음 |
| `current_product`, `product_candidates` | 확인한 상품 / 선택 후보. 후보는 최대 3개이며 상품명·제조사·용량 등을 표시하고 선택 시 원래 순서를 유지 |
| `recommended_products`, `comparison_products` | 추천 이유·주의사항이 있는 상품 카드 / 영양값·기준량이 있는 비교 상품 |
| `recipe` | 객체 또는 `null`. 제목·분량·`ingredients[].name`·`ingredients[].amount`·`steps[]`를 표시. `substitutions`, `allergen_check`, `diet_limitations`, `packaged_item_cautions`도 보존 |
| `sources` | 출처 문자열 배열. 문자열에 발행기관·자료명·쪽수 또는 절·URL이 포함될 수 있음. 없으면 출처 영역 숨김 |
| `recommended_questions`, `ui_guidance` | 후속 질문 문자열 배열 / 설정 이동 등 안내 객체 배열. 앱의 실제 이동 경로는 프론트에서 연결 |
| `safety_guidance` | 객체 또는 `null`. `urgency`, `headline`, `actions`, 선택 `emergency_contact`를 긴급 안내로 표시 |
| `assessment_summary`, `data_completeness`, `product_data_trust` | 판단 범위·자료 충실도·출처 확인 상태. 기존 `confidence`를 답변 정확도나 섭취 안전 확률로 표시하지 않음 |
| `conversation_state` | 클라이언트 문맥 방식의 다음 요청에 그대로 사용 |
| `external_ai_processing` | 현재 답변의 외부 AI 허용·사용 여부. 상세 값은 아래 참고 |

`risk_level`만으로 전체 결론을 추론하지 않습니다. `pipeline_stage`, `fallback_reason`, `source_details` 같은 내부 진단 필드는 공개 응답에 없으므로 화면 로직에서 요구하지 않습니다.

### 4. 채팅 요청 — 서버가 대화를 저장하는 방식

대화방 API는 `FOOD_CHATBOT_ENABLE_CONVERSATIONS=true`, 서비스 토큰·사용자 식별 서명, 준비된 저장소가 필요합니다. 생성 시 백엔드가 UUID를 만들고 재시도에도 같은 `conversation_id`를 사용합니다.

```json
{
  "conversation_id": "a0c888f3-c2cb-4b5d-8335-e69c2495f1d2",
  "title": "식품 질문"
}
```

위 본문을 `POST /conversations`에 보낸 뒤, 채팅은 같은 방 ID와 질문별 UUID인 `turn_id`를 포함해 `POST /chat`으로 보냅니다.

```json
{
  "conversation_id": "a0c888f3-c2cb-4b5d-8335-e69c2495f1d2",
  "turn_id": "86596e45-f3ab-4e2d-8b7e-7ba8b82f2194",
  "message": "무가당과 무설탕의 차이를 알려줘",
  "profiles": []
}
```

이 방식에서는 서버가 이력·상태를 복원하므로 **`chat_history`, `conversation_state`를 보내지 않습니다.** 개인화 질문에는 요청 시점의 최신 선택 프로필을 `profiles`에 전달합니다. 같은 질문을 재시도할 때는 같은 `turn_id`와 본문을 유지하고, 새 질문에는 새 `turn_id`를 사용합니다. HTTP 재시도의 서명 시각·nonce는 새로 만듭니다.

채팅 응답에는 `conversation_id`, `conversation_title`, `conversation_revision`, `turn_id`도 포함됩니다. 대화 재조회 시 어시스턴트 메시지의 `response`에서 채팅 응답과 같은 공개 필드를 읽습니다.

### 5. 인증과 외부 AI 동의

세 종류의 값을 분리합니다. `FOOD_CHATBOT_API_TOKEN`은 서버 간 호출 권한, `FOOD_CHATBOT_USER_IDENTITY_SECRET`은 대화 소유자 확인, `FOOD_CHATBOT_EXTERNAL_AI_CONSENT_SECRET`은 외부 AI 전송 동의 서명에 사용합니다. 서로 다른 값으로 설정하고 서명 키는 최소 32바이트의 공백 없는 표시 가능한 ASCII를 사용합니다.

| 헤더 | 전송 조건·값 |
| --- | --- |
| `X-Food-Chatbot-Token` | AI 서비스 토큰이 설정되어 있으면 `/chat`에 필수. 대화방·신고는 토큰 설정 자체가 필수. `Authorization: Bearer <AI 서비스 토큰>`도 지원하며 앱 로그인 JWT와 구분 |
| `X-Food-Chatbot-User-Id` | 로그인한 계정의 양의 정수 ID. 사용자 식별·외부 AI 동의 서명에서 공유 |
| `X-Food-Chatbot-Identity-Timestamp` | 저장형 채팅·대화방·신고에 필요한 사용자 식별 서명의 Unix 시각(초) |
| `X-Food-Chatbot-Identity-Nonce` | 사용자 식별 서명용 요청별 새 난수 |
| `X-Food-Chatbot-Identity-Signature` | 사용자 식별용 HMAC-SHA256 소문자 hex |
| `X-Food-Chatbot-External-AI-Consent` | 외부 AI 동의: `granted` 또는 `denied` |
| `X-Food-Chatbot-External-AI-Timestamp` | 외부 AI 동의 서명의 Unix 시각(초) |
| `X-Food-Chatbot-External-AI-Nonce` | 외부 AI 동의 서명용 요청별 새 난수 |
| `X-Food-Chatbot-External-AI-Signature` | 외부 AI 동의용 HMAC-SHA256 소문자 hex |

백엔드는 앱이 보낸 위 헤더를 신뢰하지 않고, 로그인·소유권·사용자 동의를 확인한 뒤 서버에서 새로 구성합니다. 두 nonce는 각각 새로 만들며 16~128자의 URL 안전 난수를 사용하면 두 검증 규격에 맞습니다.

**서명 본문 규격:** 아래 각 줄을 LF(`\n`)로 연결한 UTF-8 바이트에 HMAC-SHA256을 적용합니다. 마지막 줄 뒤 개행은 없습니다. `body_sha256`은 실제 HTTP 본문 바이트의 SHA-256 소문자 hex입니다. JSON을 한 번 직렬화한 뒤 그 바이트로 서명하고 그대로 전송합니다. `method`는 대문자, `path`는 AI 서버가 받는 경로(`/chat` 등)이며 호스트·쿼리 문자열은 포함하지 않습니다. 본문 없는 GET·DELETE는 빈 바이트의 해시를 사용합니다.

사용자 식별 서명 — 키: `FOOD_CHATBOT_USER_IDENTITY_SECRET`, 현재 보호 경로의 purpose는 `conversation`:

```text
v2
conversation
timestamp
method
path
user_id
identity_nonce
body_sha256
```

외부 AI 동의 서명 — 키: `FOOD_CHATBOT_EXTERNAL_AI_CONSENT_SECRET`:

```text
v1
timestamp
method
path
user_id
granted 또는 denied
external_ai_nonce
body_sha256
```

사용자 식별 서명의 유효기간은 기본 300초, 동의 서명은 기본 60초이며 환경변수로 설정합니다. 재사용한 nonce는 거부하고, 다중 워커·인스턴스에서는 게이트웨이 등 공유 저장소의 재사용 방지 처리가 필요합니다. 구현 기준은 `app/infrastructure/request_identity.py`, `app/infrastructure/external_ai_consent.py`이며, 동의 서명 테스트 벡터는 `tests/fixtures/chat-external-ai-consent-v1.json`에 있습니다.

RAG·LLM 실행에는 운영 설정 `FOOD_CHATBOT_ENABLE_EXTERNAL_AI=true`, 사용 가능한 제공자 설정, 유효한 `granted` 동의 서명이 필요합니다. RAG 검색에는 최신 인덱스도 필요합니다. 본문의 `externalAiConsent: true` 같은 값만으로는 동의가 부여되지 않습니다. 사용자 식별 서명은 외부 AI 동의를 대신하지 않으며, 동의 서명도 저장 대화의 사용자 식별 서명을 대신하지 않습니다.

동의 누락·거절·검증 실패 또는 외부 AI 비활성화 시 규칙 기반 답변으로 처리합니다. `external_ai_processing`은 `allowed_for_request`, `used`, `status`, `services`를 반환하며 `status`는 `used`, `allowed_not_used`, `operator_disabled`, `consent_denied`, `consent_not_verified`, `not_evaluated` 중 하나입니다. `services`는 `llm`, `rag`의 배열이며, 사용 동의가 있어도 매 질문에 외부 AI가 호출되는 것은 아닙니다.

### 6. 오류 응답

일반 오류는 `{ "detail": "설명" }`, 요청 스키마 오류는 `detail`이 오류 목록인 JSON입니다. `/ready`의 `503`은 별도의 준비 상태 객체입니다. 외부 AI 동의 실패는 서비스 인증 오류와 달리 보통 `200` 규칙 답변과 위 처리 상태로 확인합니다.

| HTTP | 의미 |
| --- | --- |
| `400`, `413` | 잘못된 요청 크기 헤더·본문 또는 본문 크기 제한 초과 |
| `401` | AI 서비스 토큰 또는 필요한 사용자 식별 서명 오류 |
| `404` | 대화방·상품 없음, 또는 대화 저장 기능 비활성화 |
| `409` | 대화 처리 충돌·용량 제한·같은 턴 ID의 다른 요청 등 |
| `422` | 필드·UUID·길이·대화 이력/상태 조합 등 입력 검증 오류 |
| `429` | 요청 제한 초과. `Retry-After` 참고 |
| `500`, `503`, `507` | 저장 데이터 복원 오류 / 준비·저장소·서버 설정 오류 / 저장할 응답 크기 초과 |
