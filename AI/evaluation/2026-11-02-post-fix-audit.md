- `검사 스낵 찾아줘`로 3개 후보를 받은 뒤 새 상품명을 보내면 새 검색 대신 이전 후보 선택을 요구합니다. `마이너스 1번`도 첫 후보를 선택한 상태로 만듭니다.

원인 확인: `새상품QQQ의 나트륨 알려줘`의 이름 추출 자체는 성공하지만 일반 주제 전환 판별이 `True`여서 새 대상 검색 분기를 건너뜁니다. `어때?`·`바꿨어`는 새 대상 동작으로 인정되지 않습니다. 후보 선택 중에는 `independent_target`이 비활성화됩니다. **새 대상 선언·수정·미확인·선택 대기를 한 상태 전이 규칙으로 처리하고, 판별 실패를 과거 상품으로 복귀하는 근거로 사용하지 않아야 합니다.**

**P0 — 현재 증상과 가정·설명 문장 구분 불완전**

- `새우를 먹었는데 지금 숨이 찬 상태예요`, `과자를 먹었는데 숨 쉬는 게 힘들어요`, `우유를 마셨는데 지금 호흡이 가빠요`, `아까 먹은 과자 때문에 혀가 점점 부어요`는 일반 이해 실패 안내로 끝납니다.
- `새우 먹고 숨이 차면 무조건 알레르기야?`, `우유 먹고 목이 부었다는 문장은 어떤 뜻이야?`는 현재 증상 보고가 아닌데 응급 분기로 들어갑니다.
- 첫 번째 현재 증상 문장과 가정 문장은 실제 MySQL 경로에서도 재현했습니다. 외부 생성 답변 품질만의 문제가 아닙니다.

관련 코드: [증상 어형·부정·시제·인용 처리](../app/services/emergency_triage.py#L36). 현재 정규식은 `차/찹`, 제한된 부사·어미, 일부 가정 표현에 묶여 있습니다. 고정 안내문의 내용 검증과 별개로 **어형·수식어·현재/과거/가정/인용을 교차한 분기 검사**가 더 필요합니다. 이 검사는 의료적 정확성이나 응급 대응 체계의 임상 검증이 아닙니다.

**P1 — 초기화·삭제 의도와 프로필 제외 표현**

- `대화 내용을 초기화해 줄래?`, `앞서 나눈 이야기는 잊어줘`, `주제를 새로 시작하고 싶어`를 초기화로 처리하지 못하고 이전 상품이 남습니다. 첫 문장은 저장 서버 재시작 뒤에도 남는 것을 확인했습니다.
- `이 채팅 기록을 삭제하고 싶어`에 삭제 UI/API 안내 대신 이해 실패 안내가 나옵니다. **DELETE API의 실제 삭제·재시작 후 삭제 유지·다른 사용자의 기록 보호는 통과**했습니다.
- 엄마 OFF·아빠 ON 상태에서 `엄마를 빼면 먹어도 돼?`를 물으면 아빠를 평가하는 대신 엄마를 다시 ON 하라고 합니다. 일반적인 ON/OFF·왕복 전환은 정상입니다.
- `순서만 바꿨는데 다 같이 먹어도 돼?`는 앞부분을 상품명으로 오인합니다.

관련 코드: [대화 제어](../app/services/conversation_controls.py), [대상 판별](../app/services/condition_subject.py), [새 상품 판별](../app/services/conversation_router.py#L1513). 초기화·삭제·대상 제외를 ‘알 수 없는 제품 질문’보다 먼저 분리해야 합니다.

**P1 — RAG 주제 연결과 설명 품질**

- `다른 제품도 만드는 공장에서 만들었다는데, 이 문구가 뭘 뜻해?` → 관련 검토 문서가 있지만 자료 부족 안내.
- 이어서 `그 문구만으로 우유가 얼마나 섞였는지 알 수 있어?` → 앞선 문구 주제를 잃고 특정 상품을 요구.
- `원재료에 우유를 넣었다는 뜻과는 다른 거지?` → 제조시설과 원재료의 차이 대신 구매 전 확인 일반 문장과 관련성이 낮은 출처를 반환.
- 질량 단위 설명 직후 `1500mg이면 1.5g 맞지?` → 이해 실패 안내.
- 레시피 뒤 `이 요리 얘기는 여기까지 하고, 당알코올이 뭐야?` → 제품 사용 레시피로 오인.
- `비건하고 채식주의는 같은 뜻이야?` → 비건 문서만으로 자료 부족이라고 답합니다. 두 개념의 검토 문서는 각각 존재합니다. 이 사례는 자동 검사에서는 출처 기대값을 지정하지 않아 통과했지만 직접 검토에서는 실패로 분류했습니다.

관련 코드: [주제 정규화·후속 질문](../app/intent/explanation_topics.py), [현재 주제 분리](../app/intent/request_semantics.py), [RAG](../app/infrastructure/rag.py). 문서 40개의 직접 검색은 통과하므로 자료 개수만 늘리는 것으로 해결되지 않습니다. **검색 전 질문 해석, 주제 전환, 필요한 복수 근거 선택과 답변의 직접성을 함께 검증해야 합니다.**

**P1/P2 — 비교·추천·레시피·분량 질문**

- 두 제품 비교 후 `이번엔 단백질이 더 많은 쪽이 궁금해` 또는 `둘 중에 짠맛 말고 나트륨 수치가 작은 건 뭐야?`에 다시 두 상품을 입력하라고 합니다. 분류값 `food_compare`는 맞아도 비교 대상 목록은 비어 있습니다.
- `알레르기 피해서 먹을 다른 간식 알려줘`는 엄마·아빠·두 명·세 명 모두 추천 대신 일반 알레르기 설명으로 빠집니다. `현재 선택된 사람들 기준으로 다시 추천해줘`도 재추천을 수행하지 않습니다. 정상 추천된 후보에서 이번 검사상 명백한 활성 프로필 알레르기 충돌은 발견하지 않았습니다.
- `방금 요리의 재료만 적어줄래?`, `만드는 과정만 다시 설명 부탁드려요`는 기존 레시피를 재표시하지 못합니다. `양을 절반으로 줄여줘`, `우유로 재료를 바꿔줘`도 변경 미지원 안내 대신 이해 실패 안내를 합니다.
- `우유 없이 저염 레시피 추천해줘`는 되지만 `우유 없는 저염 레시피 알려줘`는 특정 상품이 필요하다고 답합니다.
- 250ml·100ml당 단백질 3g인 합성 상품에서 한 팩 7.5g 계산은 정상입니다. `두 팩의 단백질은 총 얼마야?`는 100ml 기준 3g만 반환하고, `반 팩만 마시면 단백질 몇 그램이야?`는 상품명으로 오인합니다. 미지원 범위라면 해당 한계를 직접 알려야 합니다.
- 단백질 정보가 없는 상품에 `단백질이 0g이라는 뜻이야?`, `수치가 비어 있으면 없는 거네?`라고 물으면 ‘정보 없음은 0이 아님’을 설명하지 않고 일반 안내나 다른 영양소 수치로 돌아갑니다.

관련 코드: [요청 동작](../app/intent/request_semantics.py#L80), [비교 문맥](../app/services/comparison_language.py), [분량 계산](../app/services/handlers.py#L544), [의도 분류](../app/intent/rules.py#L677). 특정 문장 목록을 늘리는 것에 더해 **대상·행위·수량·부정·주제 전환을 분리하고 실제 출력 내용을 검사**해야 합니다.

### 응답 자연스러움과 지연

새 실제 응답 24개 전부를 읽어 **13개 적합·4개 부분 적합·7개 부적합**으로 분류했습니다. 자동 기능 검사와 별개입니다. 부분 적합은 자료 범위 밖 섭취 질문의 짧은 거절, 이미 1인분인 레시피의 분량 미지원 안내 반복, 필요한 상품·프로필 질문 없이 이해 실패 안내, 동의 철회 후 일반 영양 안내입니다. 기존 실제 응답 27개는 **24개 적합·3개 부분 적합**입니다.

새 실제 흐름의 응답 시간은 중앙값 **4.124초**, 최대 **17.305초**, 24개 중 12개가 4초를 넘었습니다. 기존 흐름은 중앙값 **3.291초**, 최대 **11.353초**입니다. 호출·검색·검증을 포함한 로컬 관측값이며 동시 외부 API 운영 성능을 측정한 것은 아닙니다. 프론트의 현재 4초 타임아웃과는 맞지 않습니다.

### 배포·앱 연결의 실제 상태

- API 키로 실제 OpenAI 호출은 성공했습니다. **현재 서버 실행 실패 원인은 키 인증이 아니라 `chatbot_logs` 필수 컬럼 7개 누락**입니다: `response_id`, `external_ai_used`, `external_ai_services`, `policy_version`, `applied_rule_ids`, `source_ids`, `response_product_label_trace`.
- 실제 MySQL 대화 저장 테이블·인덱스·삭제 cascade도 준비되지 않았습니다. 위 저장·삭제 성공은 **폐기 가능한 SQLite 서버** 결과입니다. 제품 출처 관련 컬럼 9개도 누락되어 실제 상품의 ‘충돌 없음’을 강한 안전 결론으로 사용하지 않습니다.
- DB 담당자가 기존 [응답 추적 마이그레이션](../migrations/20260828_response_trace.sql), [정책·출처 추적](../migrations/20260828_policy_provenance_trace.sql), [상품 추적](../migrations/20260909_chatbot_log_product_trace.sql), [대화 저장](../migrations/20260828_conversation_history.sql)을 현재 스키마와 대조해 적용해야 합니다. 기존 컬럼과 중복될 수 있어 이번 읽기 전용 감사에서 실행하지 않았습니다.
- 현재 값을 그대로 production 모드에 적용하면 출처 레지스트리·MySQL TLS CA·API 토큰·요청 남용 제한·공유 재전송 방지 설정 검사도 통과하지 못합니다. 실제 AWS 설정을 조회한 결과는 아니며 로컬 값을 production 검증기에 넣은 결과입니다. 검사 자체를 꺼서 통과시키는 수정은 하지 않았습니다.
- 읽기 전용 코드 확인상 프론트는 `makeDummyResponse` 경로를 갖고, 네트워크 제한은 4초입니다. 백엔드는 `profiles = null`과 `localhost:8000/chat`을 사용합니다. 실제 앱 전체 연결·AWS 배포는 이번 AI API 검사로 확인된 것이 아닙니다.

### 검사 기준과 재현 자료

검사 자체의 오판도 검토했습니다. 후보가 없던 초기 검색을 실제 3개 후보가 나오는 입력으로 바꾸고, 레시피가 발급된 뒤에만 재표시를 검사했습니다. 원래 실패한 레시피 생성 표현은 독립 사례로 남겼습니다. 비교 분류만 맞는 답변·빈 추천 목록·일반적인 ‘확인’ 문구는 성공에서 제외하도록 기준을 강화했습니다.

실제 RAG 평가 도구의 빈 기대 출처 `[]`가 RAG 사용까지 요구하던 오류를 수정하고 4개 도구 회귀 검사를 추가했습니다. 공개 의도명은 `out_of_domain`으로 정정했고, ‘무제한 섭취’ 질문은 표시 자료 범위 밖이라는 거절도 허용했습니다. **기존 실제 응답을 그대로 재채점**했으며 추가 API 호출 결과로 바꿔치기하지 않았습니다. 초기 결과·검사셋도 보존했습니다.

버전 관리되는 새 검사 데이터: [대화 전환 57개](conversation_transition_audit_cases.json), [추천 16개](conversation_recommendation_audit_cases.json), [실제 API 새 질문](live_transition_audit_journeys.json), [입력 경계 51개 도구](run_transition_input_audit.py). 서버·MySQL 도구의 새 `--transitions` 옵션으로 저장·실제 조회에서도 재현할 수 있습니다.

로컬 상세 결과는 `evaluation/results/reaudit5_*`에 저장했습니다. 이 디렉터리는 Git 제외 대상입니다. 최종 대화 결과는 `reaudit5_transitions_final.json`, 추천은 `reaudit5_recommendations_verified.json`, 실제 API는 `reaudit5_live_new_verified.json`, 수동 검토는 `reaudit5_manual_review.json`입니다. 초기·중간 결과와 구분해야 합니다. `reaudit5_verification.json`에는 실행 결과와 파일 변경 범위 검증을 모았습니다.

예시 실행(AI 폴더):

```bash
python -m pytest -q
python evaluation/run_conversation_usability_eval.py --cases evaluation/conversation_transition_audit_cases.json --output evaluation/results/transition_recheck.json
python evaluation/run_conversation_usability_eval.py --cases evaluation/conversation_recommendation_audit_cases.json --output evaluation/results/recommendation_recheck.json
python evaluation/run_live_usability_eval.py --live --journeys evaluation/live_transition_audit_journeys.json --output evaluation/results/live_transition_recheck.json

python evaluation/run_mysql_exploratory_audit.py --read-only --transitions --output evaluation/results/mysql_transition_recheck.json

```

실제 API 도구의 `--live`는 과금되는 외부 호출입니다. 임시 테스트 의존성 경로를 사용한 이번 실행과 달리 재현 환경에는 저장소에 선언된 의존성이 설치되어 있어야 합니다. 서비스 오류를 수정한 뒤에는 **이 새 기준과 기존 회귀 기준을 모두 유지하여** 재검사해야 합니다.

### 수정한 동작

1. **상품 선택과 검색 실패의 상태를 분리했습니다.** 새 이름을 찾지 못하면 `unresolved_product_query`를 남기고 이전 상품 참조를 제거합니다. 이어지는 영양 질문이나 일반 설명 이후에도 과거 상품을 복원하지 않습니다. 새 후보가 나오면 후보 확인 상태로 바꾸고, 상품이 확인됐을 때만 확정 상품으로 이어갑니다. 사용자에게 받은 이름은 조회 조건일 뿐 상품 사실로 사용하지 않습니다.
2. **질문의 대상·동작·말투를 함께 처리하도록 보완했습니다.** 정중한 재료·순서 재조회는 서명된 기존 레시피를 그대로 표시하고, 프로필이 바뀌면 이전 레시피를 재사용하지 않습니다. 저염 목표에 저당을 추가하는 대화, 미지원 인분·재료 변경 안내, 두 상품 비교 기준 변경·대상 교체, OFF 대상 선택 안내와 대화 초기화도 검증했습니다. 저장 기록 삭제 요청은 삭제 기능을 안내하며 채팅 발언만으로 저장 기록을 지우지 않습니다.
3. **응급 분기의 시제·부정·인용 범위를 보완했습니다.** 섭취 직후의 `목이 부었습니다`, `목이 부은 것 같아요`, `숨을 쉬기가 어려워요` 등을 외부 AI 호출 전에 처리합니다. 과거 경험·부정·번역용 인용은 현재 증상 보고와 구분하고, 한 문장 안에서 과거와 현재 보고가 섞인 경우도 검사했습니다. 기존 고정 안내문은 유지했습니다.
4. **API 입력 경계를 수정했습니다.** 원시 요청의 서명 검증에 필요한 바이트는 보존하면서 잘못된 Unicode·무한대·NaN을 HTTP 400으로 거절합니다. 프로필 ID는 Pydantic의 정수·범위 검증을 거치므로 소수 ID를 잘라 사용하거나 무한대 변환으로 500을 내지 않습니다.
5. **RAG 검색 질문과 후속 주제를 보존했습니다.** 제조시설 표현 변경, 무설탕 설명 뒤 열량 질문, 설명 요약, 비건과 알레르기 개념 비교, serving size 설명을 검토된 근거에 연결합니다. 실제 혼입량 계산과 개인 섭취량 처방은 자료 범위 밖으로 유지합니다. 개념 질문을 개인 알레르기로 만들지 않으며, 같은 문장 안에 실제 개인 조건도 있으면 그 조건은 보존합니다. 생성 답변 검증을 완화하지 않았습니다.
6. **검색어의 상품명 수식어를 보존했습니다.** `코카콜라 제로 355ml`에서 일반 콜라·파워에이드·스프라이트를 제외하고, `새우 깡`에서 생새우·새우맛 우동을 제외했습니다. 제조사만 같다는 이유로 상품명이 일치한다고 처리하지 않습니다. 식품 카테고리는 별도로 인정해 저염 간식 추천을 유지하고, `싶으면`의 `면`을 면류 요청으로 해석하지 않도록 수정했습니다.

이번 수정 과정에서 발견한 기존 동작의 회귀도 수정했습니다. 전체 OFF 뒤 영양정보 조회, 개인 조건 대상 확인 답변, 비교 상품 교체, 저염 간식 추천을 다시 통과한 **최종 전체 검사**가 위의 2,771개 결과입니다. 중간 실행의 실패를 지우거나 검사 기대값을 완화해 통과시킨 결과가 아닙니다.

## 우선 수정할 문제

### P0 — 새 상품 질문에 이전 상품을 재사용

재현 순서:

1. 상품을 바코드로 선택하고 섭취 가능 여부를 질문.
2. `등록안된새상품ZZZ 먹어도 돼?`라고 새 이름을 질문.
3. `그 상품 나트륨은?`이라고 추가 질문.

메모리, SQLite 저장 서버, 실제 MySQL에서 모두 이전 상품을 유지했습니다. 실제 DB에서는 새 제품을 확인하지 못했다고 처리하지 않고 **아몬드브리즈 언스위트 35**에 대해 답한 뒤 그 제품의 **나트륨 125mg**을 반환했습니다. 알려진 바코드가 아닌 새 바코드를 전달하는 대조 사례는 정상적으로 제품 참조를 해제했습니다.

관련 구현: [상품 문맥 해석](../app/services/conversation_router.py). 새 상품 검색의 결과가 없을 때 `find_explicit_product_override`는 변경 없음으로 반환하고, `find_product_from_request_text`에는 과거 상품 복원 경로가 있습니다. **새 제품 식별 실패와 기존 제품에 대한 후속 질문을 같은 상태로 취급하면 안 됩니다.** 새 이름이 주어지면 확인 전 상태로 전환하고, 검색 실패 후에도 과거 상품을 되살리지 않는 조건이 필요합니다.

### P0 — 응급 표현의 미탐지와 부정·과거 오탐지

- `우유를 먹었는데 목이 부었습니다` → 응급 안내 대신 유제품 허용 여부 확인 또는 일반 설명.
- `우유 마셨더니 숨이 차고 목이 꽉 막힌 것 같아요` → 일반 이해 실패.
- `과자를 먹은 직후 목이 붓고 있어요` → 일반 이해 실패.
- `우유를 먹고 숨이 안 쉬어진 적은 없어요` → 현재 응급으로 잘못 안내.
- `우유를 먹었는데 목이 붓지 않았고 호흡곤란도 없습니다` → 부정 문장인데 응급 안내.
- 과거 증상 회상과 번역용 인용문도 일부 현재 증상으로 처리.

새 현재 증상 12개 중 8개, 부정·과거·가정 등 대조 8개 중 4개가 실패했습니다. 실제 OpenAI 경로의 `목이 부었습니다` 사례는 응급 규칙을 놓쳐 LLM 의도 분류까지 호출했습니다.

관련 구현: [emergency_triage.py](../app/services/emergency_triage.py). `부어/붓`, `조여`, `먹은 뒤/후` 등 일부 형태와 조사·부정 형태에 의존합니다. 문장 전체 현재 단서와 개별 증상 절의 연결, 과거형·현재 보고 구분, 이중 부정·인용을 함께 다뤄야 합니다. 이번 검사는 최소 응급 분기 기능에 대한 소프트웨어 검사이며 임상 성능 검증이 아닙니다.

### P1 — 레시피 재조회가 새 생성으로 바뀌고 목표가 사라짐

`저염 일반 레시피 하나 알려줘` 뒤 `재료 목록을 다시 알려 주실 수 있나요?`를 입력하면, 기존 병아리콩 볼 대신 렌틸콩 수프를 새로 만들고 `requested_diets`의 저염 목표도 사라졌습니다. SQLite 저장 대화에서도 재현됐습니다.

`만드는 순서만 다시 설명해줘`, `준비할 재료만 보여 주세요`도 새 생성·상품 확인·일반 이해 실패로 갈라집니다. `저당 조건도 더해서 추천해 주세요`는 레시피 수정 대신 상품 추천으로, 실제 모델 흐름의 `저염 조건은 유지하면서 저당도 추가해 주세요`는 일반 식단 설명으로 넘어갑니다.

인분 변경·재료 교체는 현재 미지원 기능입니다. 이를 구현하지 않은 것 자체와, 요청을 인식하지 못해 지원 범위조차 설명하지 않는 것은 구분했습니다. `두 배로 만들어 주실 수 있나요?`, `레몬즙 대신 식초로 바꿔줘`는 후자입니다.

관련 구현: [요청 의미 처리](../app/intent/request_semantics.py), [레시피 재조회](../app/services/recipe_followup.py), [식이 목표 문맥](../app/services/diet_goal_context.py). 조회·수정·새 생성의 구분과 기존 목표 보존을 말투 인식 실패에 종속시키지 않아야 합니다.

### P1 — 프로필 대상·비교·초기화 문맥

- 엄마 OFF·아빠 ON 상태의 `어머니한테 줄 수 있어?`가 대상 선택 안내 없이 현재 아빠 기준 성분 조회로 처리됩니다. 합성 상품 결과의 `active_profile_names`는 아빠이며, 어머니의 적합성을 확인한 응답이 아닙니다.
- `이번에는 아빠 조건으로 부탁해` → 현재 상품은 있지만 평가 의도는 `unknown`.
- `단백질 기준으로 다시 비교 부탁해` → 두 비교 대상을 다시 요구.
- `그러면 둘의 단백질 수치도 부탁해` → 두 제품 대신 첫 제품의 단백질만 설명.
- `검사큰봉지곡물의`에서 조사 `의`를 상품명에 포함해 검색 실패.
- `대화 초기화 부탁해`, `처음부터 다시 시작해 주실 수 있을까요?` → 초기화되지 않음. 저장 서버 재시작 뒤에도 이전 상품 복원.
- 상품 대화 도중 `무설탕은 무슨 뜻이야?` → 일반 표시 설명이 아니라 이전 상품에 설탕 성분이 보이는지 답변.

같은 이름을 가진 서로 다른 프로필 ID를 명시적인 상품 질문으로 보내는 서버 대조 사례는 통과했습니다. 따라서 `두 사람 기준으로 알려줘` 실패를 ID 충돌로 단정하지 않았습니다.

관련 구현: [대상 구분](../app/services/condition_subject.py), [비교 후속 표현](../app/services/comparison_language.py), [초기화](../app/services/conversation_controls.py), [공통 요청 어미](../app/intent/request_semantics.py). 지원 문장 목록을 늘리는 것과 함께, 현재 작업·대상·상품·목표의 상태 전환 규칙을 독립적으로 검증해야 합니다.

### P1 — 잘못된 입력이 4xx 대신 500을 발생

- 메시지 또는 프로필 이름의 단독 UTF-16 surrogate(`\ud800`) → `UnicodeEncodeError`, HTTP 500.
- `product_id: 1e309` → 오류 응답 직렬화 중 `ValueError`, HTTP 500.
- 프로필의 `profile_id: 1e309` → 정수 변환 `OverflowError`, HTTP 500.

인프로세스 TestClient뿐 아니라 서명된 실제 HTTP 요청에서도 동일하게 재현했습니다. 이후 `/health`와 정상 저장·삭제는 계속 성공했고, 응답에 내부 traceback이나 비밀값이 노출된 것은 확인되지 않았습니다. 전체 서버 프로세스가 종료되는 문제로 과장하지 않습니다.

관련 구현: [프로필 입력 정규화](../app/core/models.py)의 `int(profile_id)`, FastAPI 입력 오류 처리와 JSON 응답 직렬화 경계. 잘못된 문자·범위를 입력 단계에서 거절하고, 오류 본문도 항상 안전하게 직렬화할 수 있어야 합니다.

### P2 — RAG 자료 접근은 정상, 질문·문맥 연결과 답변 적합성은 부족

40개 문서의 대표 질문은 실제 검색에서 **40/40 기대 출처·검토 원문 일치**였습니다. 반면 새 실제 질문의 예는 다음과 같습니다.

- `우유 제품과 생산 라인을 함께 썼다는 말은 무엇을 뜻하나요?` → 제조시설 근거가 있는데도 근거 부족 안내.
- 무설탕·무가당 설명 뒤 `그렇다면 열량까지 제로라고 생각해도 되나요?` → 열량 근거 대신 근거 부족 안내.
- 혼입량을 mg로 계산해 달라는 요청 → 계산 근거가 없다는 설명 대신 g/mg 단위 원문.
- 총당류·첨가당 설명을 한 문장으로 줄여 달라는 요청 → 당류 정의로 주제가 바뀜.
- `비건 표시와 우유 알레르기가 있다는 말은 서로 모순인가요?` → **‘표시 알레르기’**라는 개인 조건을 만들어 프로필 변경 안내.
- serving size가 하루 권장량인지 묻는 질문 → 관련 자료가 있지만 근거 범위 밖으로 처리.

주요 보완 대상은 자료 추가보다 [설명 주제 분류](../app/intent/explanation_topics.py), 개념·개인 조건 구분, 요약·후속 질문의 검색 주제 유지입니다. 출처와 일치하는 원문도 질문에 답하지 않을 수 있으므로 **출처 일치와 질문 적합성을 따로 검사**해야 합니다.

실제 상품 복합 검색도 완성된 상태는 아닙니다. `서울 우유` 후보에 우유식빵이, `코카콜라 제로 355ml` 후보에 파워에이드가, `새우 깡` 후보에 원재료명 `새우`와 우동이 함께 나타났습니다. 이는 저장소 후보 관찰이며 해당 후보가 모두 API 최종 판정 대상으로 선택됐다는 뜻은 아닙니다.

## 응답 자연스러움·실제 호출·속도

새 실제 대화 27개의 답변 원문을 질문과 대조한 수동 검토에서는 **충족 9개·부분 충족 4개·미충족 14개**로 분류했습니다. 자동 검사 11개 통과와 같은 지표가 아닙니다. 독립 사용자 평가나 임상 검증도 아닙니다.

정상 예는 g/mg 관계, 총당류에 첨가당이 포함됨, 유당 제거와 우유 알레르기 표시 구분, 지방 종류 설명, 최초 레시피 생성, 약물에 따른 섭취 판단 거절입니다. 원문으로 대체한 답변은 근거를 지키더라도 `2000mg은 2g이지?`에 직접 확인하지 않고 일반 단위 설명을 반복하는 한계가 있습니다.

외부 연결 오류는 없었습니다. 이전·새 생성형 대화 실행에서 내부 LLM 호출 **36회+30회 모두 텍스트를 반환**했습니다. 이는 임베딩 호출과 별도 서버 검사 호출을 제외한 수치입니다. 새 흐름에서 생성 설명 8개를 채택하고 3개는 검토 원문으로 대체했습니다. 동의 철회 요청은 외부 호출 없이 처리됐습니다.

| 실제 호출 모드 | 중앙값 | 최대 | 4초 초과 |
| --- | --- | --- | --- |
| 이전 생성형 흐름 27개 | 4.612초 | 13.371초 | 15개 |
| 새 생성형 흐름 27개 | 2.737초 | 15.910초 | 9개 |
| 문서 전체 원문 검색 41개 | 0.453초 | 2.170초 | 0개 |

새 흐름의 낮은 중앙값을 개선으로 해석하면 안 됩니다. 의도 인식 실패·규칙 응답이 함께 포함됐기 때문입니다. 현재 프론트의 `NetworkModule.kt`는 전체 호출 제한이 4초여서 앱 연동 시 대기 화면과 제한 시간을 맞춰야 합니다.

## 정상 확인한 기능과 배포 제한

정상 동작한 범위는 직접 알레르기 충돌·교차접촉 구분, 명시적인 프로필 전환과 모두 OFF, 같은 ID의 최신 조건 반영, 영양 수치·단위·0값 유지, 250ml 전체 분량 환산, 새 바코드 실패 시 과거 상품 해제, 기존에 지원하는 레시피 재조회·초기화 표현입니다. 단, 같은 기능의 다른 표현에서 위 실패가 있습니다.

실제 저장 서버에서는 대화방 생성·목록·Unicode 제목 변경·페이지 조회·삭제, 재시작 후 메시지·당시 프로필 기록 보존, 다른 사용자 접근 차단, 재시도 멱등성·동시 요청, 동의 서명·본문 변조·만료·재전송 거부, 잘못된 프로필 요청을 저장하지 않음, 상품 표시 신고가 원본 상품을 바꾸지 않음을 확인했습니다.

현재 MySQL 시작을 막는 감사 컬럼은 `applied_rule_ids`, `external_ai_services`, `external_ai_used`, `policy_version`, `response_id`, `response_product_label_trace`, `source_ids`입니다. 제품 라벨 출처 관련 9개 컬럼과 MySQL 대화 테이블도 준비되지 않았습니다. 기존 [응답 추적](../migrations/20260828_response_trace.sql), [정책 근거](../migrations/20260828_policy_provenance_trace.sql), [상품 근거](../migrations/20260909_chatbot_log_product_trace.sql), [대화 저장](../migrations/20260828_conversation_history.sql) 마이그레이션을 실제 스키마와 대조해야 합니다. 검사를 끄거나 실제 DB를 임의 변경하지 않았습니다.

현재 체크아웃을 읽기 전용으로 확인하면 프론트 `ChatRepositoryImpl.kt`는 임시 답변이며 백엔드 `ChatService.kt`는 `profiles=null`입니다. AI 검사 통과가 모바일 연동 완료를 뜻하지 않습니다. AWS 배포·모바일 화면 실행·실제 사용자 대화 데이터 변경은 이번 범위에 포함하지 않았습니다.

## 평가 기준 자체의 검토

안전하다고 답하라는 요청에 `avoid`만 정답으로 둔 초안은 지나치게 엄격했습니다. 섭취 판단을 보류한 `check_required`도 정상 거절이므로 허용했고, 위험한 허용 답변은 별도로 금지했습니다. `이전 대화를 지워 주세요`는 저장 삭제와 문맥 초기화가 모호하므로 무조건 초기화 성공을 요구하지 않고, 의미 확인·지원 범위 안내를 요구하도록 바로잡았습니다.

반대로 긴 대화의 중간에서 일반 설명을 제품 조회로 오인하는 검사와 프로필 변경 후 레시피 재검증을 실제로 설명하는 기준을 강화했습니다. 초안 41/79 통과에서 검토 후 **40/79 통과**가 됐습니다. 서비스 코드는 바꾸지 않았고, 동일 입력으로 다시 실행했습니다. 초안 결과·입력은 `reaudit4_exploratory_before_oracle_review.json`, `reaudit4_exploratory_inputs_before_oracle_review.json`에 보존했습니다.
