# 2026-11-02 챗봇 오류 수정 및 재검증

> 이후 새 질문·실제 서비스 검사를 확장하면서 추가 오류를 확인했습니다. 현재 상태는 [수정 후 독립 재검사](2026-11-02-post-fix-audit.md)를 참고하세요. 아래 통과 기록은 당시 고정 검사 범위의 결과입니다.

[수정 전 독립 검사](2026-11-02-independent-audit.md)에서 발견한 실패를 재현한 뒤, AI 디렉터리의 분류·문맥·검색 처리를 수정했습니다. 프론트·백엔드 코드, `.env`, 실제 MySQL 데이터·스키마는 변경하지 않았습니다.

공통 언어 처리는 [request_semantics.py](../app/intent/request_semantics.py)에 두었습니다. 개별 실패 문장만 추가하는 대신 요청 어미·대상·행동을 조합하고, 이전 주제를 끝내는 말과 확인 질문을 중단하는 말을 구분합니다. 기존 동의 검증, 제품 재조회, 출처 검증, 서버 준비 상태 검사를 우회하지 않습니다.

레시피 **특정 재료 삭제·인분 환산 기능을 새로 구현한 것은 아닙니다.** 이 요청을 엉뚱한 상품 검색으로 보내지 않고 미지원 이유를 안내하며 기존 레시피를 유지합니다. 지원하는 후속 기능은 기존 재료·조리 순서 재조회와 새 조건을 적용한 레시피 요청입니다.

## 실제 호출과 사람이 확인한 응답 품질

실제 OpenAI 평가에서는 27개 요청이 모두 HTTP 200이었고, 내부 LLM 호출 36회 모두 텍스트를 반환했습니다. 승인 자료 기반 생성 설명 15개를 채택했고, 2개는 생성 검증 실패로 검토된 원문을 반환했습니다. 근거 밖 질문 2개는 근거의 한계를 안내했습니다. 동의 철회 요청에서는 외부 호출이 없었습니다.

무가당→열량→쉬운 요약, 제조설비→함유 표시→혼입량, mg/g 단위, 총당류·첨가당 전환, 레시피 재료 조회를 실제 응답 원문으로 확인했습니다. 개념 질문이 개인 알레르기로 저장되거나 제품 평가로 바뀌지 않았습니다.

**자동 통과와 자연스러운 답변 완성도는 구분합니다.** `비건이면서 우유 알레르기가 있다는 게 가능한 뜻이야?`, `유당불내증이 우유 알레르기랑 같다는 뜻은 아닌 거지?`는 생성 검증 후 원문 설명으로 돌아갔습니다. 제품 표시의 해석 범위는 지켰지만 질문에 직접 답하는 정도는 제한적입니다. 증상 부정 진술과 외부 AI 동의 철회 후 응답도 일반 안내 수준이며, 모든 표현에 매끄럽게 답한다고 평가하지 않습니다.

27개 요청의 응답 시간은 중앙값 **5.058초**, 최대 **13.192초**, 16개가 4초를 넘었습니다. 모델 요청과 규칙 요청을 함께 센 로컬 측정치입니다. 프론트의 기존 4초 제한과 대기 화면은 앱 담당자가 맞춰야 합니다.

실제 DB에서 `매일 우유`의 첫 후보가 `매일우유`로 개선됐고, 명시적으로 용량이 다른 150ml 상품은 500ml 검색에서 제외됐습니다. 다만 복합 이름·일반명 대응과 카탈로그 품질까지 해결된 것은 아닙니다. `서울우유 흰우유`, `삼다수 500ml`은 현재 API에서 정확한 제품을 확인하지 못해 바코드 등 추가 정보를 요청합니다. 저장소의 부분 일치 후보를 실제 섭취 판정 대상으로 임의 확정하지 않는 것도 확인했습니다.

## 서버·저장·배포 범위

실제 서버 프로세스와 임시 SQLite로 다음 흐름을 검증했습니다.

- 엄마→아빠→모두 OFF→재선택, 동일 프로필 ID의 조건 변경, 과거 답변의 당시 프로필 기록 보존.
- 대화방 생성·목록·제목 변경·페이지 조회·삭제 및 재시작 후 삭제 유지.
- 존댓말 초기화 후 서버를 다시 시작해도 이전 상품을 복원하지 않음.
- 다른 사용자 접근 거부, 요청 위변조·만료·재전송 차단, 중복 저장 방지, 동시 요청 충돌 처리.

**현재 `.env` 그대로의 MySQL 서버 시작은 여전히 실패합니다.** 실제 `app.start`가 감사 로그 컬럼 7개 누락으로 종료 코드 3을 반환했습니다. 메모리 저장소로 분리한 실제 서버의 `/health`, `/ready`, `/openapi.json`, `/chat`는 모두 200입니다.

필요한 DB 작업은 기존 [응답 추적](../migrations/20260828_response_trace.sql), [정책 근거](../migrations/20260828_policy_provenance_trace.sql), [상품 근거](../migrations/20260909_chatbot_log_product_trace.sql) 마이그레이션과 실제 스키마의 대조입니다. 제품 라벨 출처 컬럼 9개 및 MySQL 대화 저장 테이블도 준비되지 않았습니다. 실제 MySQL 저장·삭제 성공이나 AWS 배포 완료를 확인한 것은 아닙니다. 기존 준비 상태 검사를 끄거나 실제 DB를 임의 변경하지 않았습니다.

앱의 프로필·동의 서명·대화 상태 중계 및 운영 인증·TLS 등 남은 연동 조건은 [수정 전 검사 보고서의 배포 준비 항목](2026-11-02-independent-audit.md#현재-서버-시작과-배포-준비)에 있습니다. 이번 AI 내부 수정으로 그 작업까지 완료된 것은 아닙니다.

## 재현 방법과 증거

`AI/`에서 프로젝트 의존성을 설치한 Python으로 실행합니다. 실제 호출은 설정된 키를 사용하며 비용이 발생합니다.

```bash
python -m pytest -q
python evaluation/run_conversation_usability_eval.py --cases evaluation/conversation_holdout_cases.json
python evaluation/run_live_usability_eval.py --live --journeys evaluation/live_holdout_journeys.json
python evaluation/run_mysql_readonly_audit.py --read-only --extended
python evaluation/run_server_acceptance_eval.py --extended
python evaluation/run_api_stability_eval.py --requests 96 --workers 8
```

이번 환경은 선언된 `pypdf`를 임시 의존성 경로에 설치해 검사했습니다. 실제 상품 조회는 MySQL, 대화 저장은 임시 SQLite, 대량 자동 검사는 메모리·모의 모델을 사용했습니다. 서로 다른 환경의 통과 결과를 MySQL 전체 기능 통과로 합산하지 않습니다.

Git에서 제외된 상세 결과는 `evaluation/results/fix3_*`에 있습니다. 최종 요약은 `fix3_verification.json`, 실제 응답은 `fix3_live_holdout_final.json`, `fix3_mysql_extended_final.json`, `fix3_server_extended_final.json`, `fix3_actual_startup_final.json`, `fix3_search_identity_live.json`입니다. 이 문서와 고정 평가 입력·새 회귀 테스트는 결과 파일 없이도 변경 범위와 재현 기준을 확인할 수 있습니다.
