# 실제 연결·새 대화 시나리오 재점검

이 문서는 **수정 전 독립 검사 기록**과 이후 수정 결과를 함께 보관한다. 아래 기존 검사에서는 응급 안내 누락, OFF 대상의 다른 프로필 대체, 레시피 제외 조건 누락을 재현했다. 이후 AI 코드 수정으로 새 대화 기준 70개를 모두 충족했다. 현재 `.env`를 그대로 사용한 서버 시작은 여전히 MySQL 감사 로그 스키마 부족으로 실패한다. 최종 수정·검증 기록은 이 문서 마지막 절에 있다.

최초 검사 단계에서는 검사 도구·평가 자료·기록만 보강했고 서비스 로직은 변경하지 않았다. 이후 수정 단계도 `AI/` 내부에 한정했다. 실제 DB 데이터·스키마, 프론트·백엔드·`.env`는 변경하지 않았고 커밋·푸시하지 않았다.

## 수정 전 실행 결과

| 구분 | 결과 | 확인 범위 |
| --- | --- | --- |
| 기존 전체 pytest | **2,349 통과**, 251.26초 | 기존 회귀 검사. 이전 40개 대화 수용 기준 포함 |
| 평가 도구 변경 후 관련 재검증 | **83 통과**, 24.03초 | 기존 전체 검사와 중복. 대화 수용 기준·공개 응답 계약·근거 평가 검사 |
| 새 독립 대화 평가 | **70개 중 39 충족 / 31 미충족** | 126개 HTTP 요청 모두 200. 응답 내용·대상·문맥 기준은 별도 평가 |
| 실제 OpenAI | **21개 요청 모두 HTTP 200** | 새 질문 20개와 동의 철회 1개. 외부 AI 사용 16개, LLM 호출 23개 모두 텍스트 반환 |
| 실제 RAG 출처 | **13개 중 기대 출처 집합 일치 4개** | 8개 요청에서 실제 RAG 사용. 일반 생성 4개 채택, 4개는 검증 후 검토된 본문으로 대체 |
| 실제 답변 직접 검토 | 충족 8 / 부분 충족 2 / 미충족 11 | 질문 완결성, 문맥, 표현, 레시피·응급 동작을 함께 검토한 주관적 판정 |
| 실제 별도 서버 + OpenAI | **38/38 통과** | 실제 프로세스·로컬 HTTP·임시 SQLite 저장·재시작·삭제·서명·프로필 전환 |
| 서버 추가 검사 | **43/43 통과** | 위 검사와 중복. 외부 AI 없이 신고 API·서명 nonce 재사용 차단 추가 |
| 실제 MySQL | **26개 읽기 사례, 조회 예외 0** | 12개 검색어, 실제 상품 판정·후속 질문·후보 선택·단위 매핑. 별도 무결성 기준 6/6 |
| 현재 설정 서버 시작 | **실패, 종료 코드 3** | `chatbot_logs` 필수 열 7개 누락 |
| 임시 메모리 서버 시작 | 정상 | `/health`, `/ready`, `/openapi.json`, `/chat` 모두 200 |

70개는 경계 상황을 의도적으로 고른 수용 기준이다. 31개 미충족은 서로 다른 버그 31개나 전체 질문의 오류율을 뜻하지 않는다. 같은 레시피 분류 오류가 여러 프로필 시나리오에 반복된다. 통과 역시 그 사례에 지정한 기준만 충족했다는 의미다. 예를 들어 과거·가정 표현을 현재 응급 상황으로 분류하지 않는 검사는 의학 설명의 품질까지 평가하지 않는다.

출처 검사는 정확한 인용 집합을 비교한다. `lactose:0`은 관련 락토프리 근거를 찾았지만 불필요한 단백질 자료도 붙어 자동 기준에는 실패했다. 직접 검토에서는 질문의 핵심에는 답했으므로 부분 충족으로 분리했다. 생성 답변의 검증 실패 자체는 방어 동작이며, 잘못된 주제를 검색해 원문으로 되돌아가도 질문에 답하지 못하는 문제와 구분해야 한다.

## 최초 발견 문제와 당시 우선순위

### 1. 응급 표현과 질문 대상 보호

- `urgent_followup`: 우유 알레르기 프로필로 상품을 확인한 뒤 **“먹었는데 숨이 안 쉬어져”** → 일반적인 질문 이해 실패 응답.
- `emergency_variants_1`, `emergency_variants_2`: **“우유 먹고 숨쉬기 어려워”**, **“우유 먹었는데 호흡이 어려워요”** → 응급 안내 대신 성분 설명.
- `domain:1` 실제 OpenAI: **“우유 알레르기가 있는데 먹고 숨쉬기 어려워”** → 외부 AI를 호출한 뒤 구매 전 표시 확인 자료로 응답.
- `emergency_scope_2`: **“우유 먹고 지금 숨이 안 쉬어지는 건 아니야”** → 현재 응급 상황으로 오인.
- `off_subject_1`, `off_subject_2`: 엄마 ON으로 우유 충돌 확인 → 엄마 OFF·아빠 ON → **“엄마는요?”** 또는 **“그럼 엄마는요??”** → 아빠 조건의 ‘직접 충돌을 찾지 못함’ 응답. 최종 판정이 `check_required`여도 질문 대상이 잘못 연결된 결함이다.
- `off_subject_0`, `active_subject_0`: **“엄마도🙂”**, **“아빠도🙂”**를 일반적인 이해 실패로 처리. 실제 DB에서는 전자를 상품 검색 후보로 연결하기도 했다.

원인 확인 위치: [emergency_triage.py](../app/services/emergency_triage.py)의 중증 표현·현재성·알레르기 문맥 판정, [condition_subject.py](../app/services/condition_subject.py)의 이름 경계와 짧은 후속 질문 판정. `어렵`과 실제 활용형 `어려워`, `는요`·이모지, 직전 상품 문맥, 문장 부정 범위를 구분하는 보완이 필요하다. 고정 응급 경로와 대상 확인은 검색·생성보다 먼저 적용해야 한다.

### 2. 레시피의 제외 조건·이전 목표 유지

- `recipe_new_3`: **“우유 없이 저염 레시피 추천해줘” → “당근 없이 만들어줄래?”** → 당근이 포함된 렌틸콩 수프를 반환하며 `requested_diets`의 저염식도 삭제된다.
- `diet_followup_add`: **“저염 레시피 추천해줘” → “고단백도 같이 적용한 다른 레시피 추천해줘”** → 저염 목표가 사라지고 제품을 찾으라는 응답. 제품 없는 일반 레시피임을 명시해도 같은 문제가 남는다.
- `recipe_profile_constraints_*`, `recipe_profile_controls_*`: **“간단한 한 끼 레시피 추천해줘”**, **“제품 없는 일반 레시피 추천해줘”** → 제품 없는 일반 레시피로 다시 요청하라는 응답. 프로필별 재료 검증까지 도달하지 못했으므로 이 사례들을 재료 검증의 실패로 단정하지 않는다.
- `recipe_new_1`, 실제 `recipe:1`: **“재료 목록만 다시 보여줘/정리해줘”** → 이해 실패.
- `recipe_new_2`, 실제 `recipe:2`: **“이걸 3인분으로 바꿔줘/3인분으로 바꿔줄래?”** → 지원 범위 설명 없이 이해 실패.

확인 위치: [recipe.py](../app/services/recipe.py)의 `_requested_diets`, [recipe_followup.py](../app/services/recipe_followup.py), [conversation_router.py](../app/services/conversation_router.py). 편집 기능을 새로 구현하지 않더라도 지원하지 않는 요청을 정확히 안내하고 기존 목표를 유지해야 한다. 조건을 무시한 새 레시피를 수정 완료처럼 반환하면 안 된다.

### 3. AWS 시작에 필요한 DB·운영 설정

실제 MySQL 로그인과 상품 조회는 성공한다. 현재 서버의 직접적인 시작 실패 원인은 감사 로그 스키마다. 누락 열은 다음 7개다.

`response_id`, `external_ai_used`, `external_ai_services`, `policy_version`, `applied_rule_ids`, `source_ids`, `response_product_label_trace`

기존 마이그레이션은 [응답 추적](../migrations/20260828_response_trace.sql), [정책 출처 추적](../migrations/20260828_policy_provenance_trace.sql), [상품 근거 추적](../migrations/20260909_chatbot_log_product_trace.sql)에 있다. 기존 열·인덱스·버전을 확인한 뒤 DB 담당자와 적용해야 한다. 이번 검사에서 실행하지 않았다.

그 밖의 현재 상태:

- 상품의 출처·수집 시점·내용 버전 등 lineage 필드 9개가 부족하다. 조회 가능성과 알레르기 ‘없음’을 뒷받침하는 근거 준비 여부는 다르다.
- MySQL 대화 저장 스키마가 준비되지 않았고 현재 대화 저장 설정도 OFF다. 실제 MySQL 저장·삭제는 검증하지 못했다. 저장·재시작·삭제 통과는 임시 SQLite 결과다.
- 현재 값을 production 환경으로 검사하면 출처 레지스트리, MySQL TLS CA, 서비스 토큰 길이, 요청 제한 경계, 공유 재전송 방지 설정에서 오류가 난다. 개발 환경 값으로 확인한 결과이며 AWS의 실제 설정을 읽은 것은 아니다.

### 4. RAG 질문 분류와 대화 문맥

- `sugar:1–2`: 무가당·제로슈거 차이를 설명한 뒤 **“그 말은 에너지도 아예 없다는 거지?”**, **“중학생도 이해하게 딱 두 문장으로 설명해줄래?”** → 일반 영양 안내로 전환.
- `facility:0–1`: **“땅콩 제품이랑 생산 라인을 같이 쓴다는 문구…”**를 제조시설 공유 주제와 연결하지 못함.
- `lactose:1`, `definition_not_personal_1`: 개념을 묻는 질문을 개인 알레르기 입력으로 오인. “이번 질문에 적은 알레르기만 임시로 반영했어요”라는 부적절한 안내가 붙음.
- `label:0`: **“영양정보에 0g이면 진짜 한 방울도 없는 거야?”** → 제품 식별자 요구.
- `label:1`: 1회 제공량과 권장량의 차이를 묻는데 표시 기준량 설명만 반환.
- `sodium:2`: **“출처를 한 줄만 붙여서 요약해줘”** → 이전 나트륨·소금 주제 소실.

확인 위치: [explanation_topics.py](../app/intent/explanation_topics.py), [request_language.py](../app/services/request_language.py), [message_constraint_guard.py](../app/services/message_constraint_guard.py). 이번 재현은 주로 검색 전 분류·문맥 복원에서 발생했다. 모델은 요청한 `gpt-6-sol`, 임베딩은 `text-embedding-3-large`를 사용했고 실제 응답을 받았다.

### 5. 복합 질문·선택·초기화의 응답 완결성

- `compound_3`: **“원재료랑 열량을 한 번에 보여줘”** → 원재료만 제공.
- `volume_without_package`: **“한 통을 다 마시면…”** → 총량 계산에 필요한 포장 용량을 안내하지 않고 100ml 수치를 반환. 기준량 표시는 있지만 총량 질문에는 답하지 못함.
- `compare_multi_axes`: 비교 뒤 **“단백질이랑 칼로리도 같이 비교해줘”** → 단백질을 제품명으로 검색.
- `compare_cancel`: 비교 취소 후 **“그럼 뭐가 더 낮아?”** → 문장은 비교 제품을 요청하지만 `current_product`·`overall_decision`에는 이전 우유의 `avoid`가 복구됨. 화면이 구조화된 판정을 사용하면 본문과 다른 인상을 줄 수 있음.
- `candidate_new_0`: **“맨 아래 걸로 할게”** → 후보 미선택.
- `candidate_new_1`: **“두번째 제품으로 할게”** → 선택된 상품은 맞으나 답변은 이해 실패. 상품 식별자만 검사하면 놓치는 문제다.
- `candidate_search_without_space`: 가상 검색어 **“검사 스낵”**은 후보 3개, **“검사스낵”**은 후보 없음. 합성 카탈로그 재현이며 실제 모든 상품의 띄어쓰기 검색 성능으로 일반화하지 않는다.
- `reset_new_2–3`: **“대화 초기화해줘”**, **“처음부터 다시 할게”** → 이전 상품 유지.
- `help_followed_profile`: **“왜 그런지 쉬운 말로 알려줘”** → 이전 판정 이유 설명 대신 이해 실패.

## 정상 확인한 동작과 사용성 한계

명시적인 프로필 전환·전체 OFF·다시 ON, 알 수 없는 새 바코드에서 이전 상품 사용 차단, 단백질·나트륨 복수 조회, 0과 결측치 구분, 지방·포화지방 분리, 새 제품으로 전환, 일부 후보 정정, 기존 조리 순서 재표시와 조건 변경 시 재표시 거부, 대체 상품의 충돌 후보 제외는 지정한 사례에서 통과했다. 답변의 자연스러움은 표현에 따라 차이가 크며 익숙한 문장만 반복하는 시연으로는 위 결함이 가려질 수 있다.

서버 검사에서는 다음도 확인했다.

- 저장 후 두 차례 재시작, 대화 원문·제목·당시 프로필 스냅샷 유지.
- 대화방 간 문맥 분리, 타 사용자 조회·수정·삭제·추가 거부.
- 동일 요청 재시도와 동시 중복 요청에서 저장 메시지 2개만 유지. 같은 턴 ID의 다른 본문·프로필은 409.
- 목록·메시지 페이지 조회 누락·중복 없음, 삭제 시 DB 행 제거, 재시작 뒤 삭제 유지.
- 제품 표시 신고 202, 잘못된 신고 422, 미등록 상품 신고 404, 신고로 상품 행이 변경되지 않음.
- 요청별 동의 확인, 동의 철회 시 외부 호출 없음, 사용자 식별 서명 nonce 재사용 거부.

실제 신규 요청 21개의 응답 시간은 **6ms~10.932초, 중앙값 1.937초**, **8개가 4초 초과**였다. 비호출·즉시 거절도 포함한 수치여서 생성 응답 전체의 속도 대표값으로 사용할 수는 없다. 프론트 공통 HTTP 제한은 4초다. 현재 `ChatRepositoryImpl`은 더미 응답이며, 백엔드 `ChatService`는 `localhost:8000`, `profiles=null`과 단일 프로필을 사용하고 서명 동의·구조화된 대화 상태 연결이 없다. 실제 앱 연결 시 담당 팀원과 이 부분을 맞춰야 한다. 파일은 읽기만 했다.

- 새 실제 AI 질문: [live_extended_journeys.json](live_extended_journeys.json), [실행기](run_live_usability_eval.py)
- 실제 DB 읽기: [run_mysql_readonly_audit.py](run_mysql_readonly_audit.py)
- 실제 서버: [run_server_acceptance_eval.py](run_server_acceptance_eval.py)
- 종합 기록: `results/reaudit2_verification.json`
- 대화 원문: `results/reaudit2_extended.json`, `results/reaudit2_live_extended.json`
- 실제 응답의 추가 의미 검사·직접 검토: `results/reaudit2_live_reviewed.json`
- DB·서버: `results/reaudit2_mysql.json`, `results/reaudit2_actual_startup.json`, `results/reaudit2_server_live.json`, `results/reaudit2_server_extended.json`

`results/`는 Git 제외 경로다. 실패 기준도 평가 자료에 남겼으며, 기대값을 현재 동작에 맞춰 성공으로 바꾸지 않았다. 검토 중 단순한 열량/칼로리 용어 차이, 정확히 세 번째를 고른 선택, `profile_based_recheck` 명칭은 결함에서 제외했다. 반대로 상품 선택만 성공하고 답변은 실패한 경우와 응급·레시피 의미 검사는 저장된 실제 응답을 추가로 검사했다. 같은 응답을 다시 검사한 경우를 새로운 API 호출로 세지 않았다.

AI 디렉터리에서 의존성을 준비한 환경의 Python으로 실행한다. 이번 로컬 실행은 기존 Python 3.13.5와 선언된 `pypdf`를 제공하는 임시 의존성 경로를 사용했다. 새 환경에 의존성을 설치하거나 AWS·모바일 실기기를 검증한 결과는 아니다.

```bash
python -m pytest -q --disable-warnings
python evaluation/run_conversation_usability_eval.py --cases evaluation/conversation_extended_cases.json --output evaluation/results/extended.json
python evaluation/run_live_usability_eval.py --live --journeys evaluation/live_extended_journeys.json --output evaluation/results/live_extended.json
python evaluation/run_mysql_readonly_audit.py --read-only --output evaluation/results/mysql_readonly.json
python evaluation/run_server_acceptance_eval.py --live --output evaluation/results/server_live.json
```

`--live`는 실제 유료 OpenAI 호출을 허용한다. 최초 검사 당시 새 대화·실제 AI 평가는 미충족 기준으로 종료 코드 1을 반환했다. 이를 서버 실행 실패나 API 인증 실패로 혼동하지 않아야 한다. 수정 후 최종 결과는 아래에 구분한다.

## 우선순위 수정 완료 기록

AI 내부에서 수정할 수 있는 항목을 우선순위대로 반영했다. 아래는 최초 검사 기록과 구분한 최종 결과다.

| 우선순위 | 수정 결과 |
| --- | --- |
| 1. 응급·질문 대상 | “숨쉬기 어려워”, “호흡이 어려워요”, 상품 확인 후 “먹었는데 숨이 안 쉬어져”를 검색·LLM 호출 전에 처리. 현재 증상의 부정 표현도 구분. “엄마는요?”, “엄마도🙂”에서 엄마가 OFF면 다른 ON 프로필로 대체하지 않음 |
| 2. 레시피 조건·후속 질문 | 저염 뒤 고단백을 추가하면 이전 목표를 유지. 제품 없는 일반 레시피·한 끼 표현을 인식. 서명된 이전 레시피의 재료와 조리 순서를 재표시. 특정 재료 삭제·인분 자동 조정은 미지원임을 안내하며 수정 완료처럼 새 레시피를 반환하지 않음 |
| 3. 배포 준비 | 실제 DB 로그인·상품 조회 성공과 서버 시작 실패를 분리 확인. 누락된 감사 로그 열 7개와 기존 마이그레이션을 확인했으며 준비 검사는 유지. 실제 DB 변경은 미실행 |
| 4. RAG | 생산 라인 공유, 무첨가·제로, 에너지 후속 질문, 0g·권장량·유당 관련 표현을 기존 검토 자료에 연결. 요약·쉬운 설명에서도 주제 유지. 개념 질문을 개인 알레르기 입력으로 오인하지 않도록 보완. 혼입 확률 요청은 수치 근거 한계를 안내 |
| 5. 대화 완결성 | 복수 영양소 비교·원재료와 열량 복합 질문, 전체 포장 계산에 필요한 용량·단위 확인, 후보 선택 표현, 초기화, 판정 이유 후속 설명 개선. 비교 취소 후 이전 상품을 복구하지 않으며 새 비교 입력을 요청 |

기존 동작과의 충돌도 수정했다. “유제품 없이”를 “제품 없이”로 읽지 않도록 단어 경계를 적용했고, 비교 후 새 상품을 선택하면 “그럼 단백질은?”은 새 상품으로 연결한다. 평가 도구는 각 요청 당시의 대화 기록을 복사해 저장하므로 이후 질문이 과거 요청 기록에 덧붙지 않는다.

### 최종 검증

| 검사 | 최종 결과 |
| --- | --- |
| 전체 자동 검사 | **2,447 통과**, 178.43초. 이번에 회귀 검사 98개 추가; 외부 AI 없는 격리 검사 |
| 새 대화 기준 | **39/70 → 70/70**, 126개 HTTP 요청 모두 200. 기존에 실패한 31개 사례 해결 |
| 실제 OpenAI | **21/21 요청 기준 충족**, 실제 LLM 호출 27회 모두 텍스트 반환. 외부 처리 사용 14개 요청 |
| 실제 RAG 출처 | **4/13 → 13/13** 기대 출처 집합 일치. 생성 답변 11개 채택, 2개는 검증 후 검토된 원문으로 대체 |
| 실제 답변 직접 검토 | 충족 20 / 부분 충족 1. 유당불내증 후속 질문은 관련 검토 본문으로 연결되지만 개념 자체에 대한 직접 설명은 제한적 |

| 실제 MySQL | **26개 읽기 사례**, 12개 검색어, 조회 예외 0. 단위·후보 선택·OFF 대상·응급 처리 등 추가 기준 **8/8** |
| 현재 `.env` 서버 시작 | 감사 로그 스키마 부족으로 **종료 코드 3**. 격리 메모리 설정의 `/health`, `/ready`, `/openapi.json`, `/chat`은 모두 200 |

최종 OpenAI 검사에서는 `gpt-6-sol`과 `text-embedding-3-large`를 사용했다. 응답 시간은 4ms~10.993초, 중앙값 4.424초이며 21개 중 12개가 4초를 넘었다. 즉시 응답·비호출 사례가 섞여 있으므로 생성 모델 자체의 속도나 AWS 성능을 나타내는 수치는 아니다. 생성 답변이 검증을 통과하지 못하면 원문으로 대체하므로 요청한 길이·문체를 항상 맞추지는 못한다. 검증 조건을 완화하지 않았다.

70개 기준 중 복합 비교는 열량·칼로리의 동의어를 인정하면서 실제 수치를 모두 요구하도록 정리했다. 비교 취소 뒤 필요한 입력을 안내하는 기준과 혼입 확률의 근거 한계 안내 기준은 추가했다. 기본 오류를 숨기기 위해 상품 식별·수치·대상·제외 조건 기준을 삭제하지 않았다. 자동 검사와 개별 시나리오는 중복되므로 합산하지 않는다.

### 합치기·배포 때 넘길 작업

1. **DB 담당자:** 실제 열·인덱스·적용 이력을 확인한 뒤 [응답 추적](../migrations/20260828_response_trace.sql), [정책 근거 추적](../migrations/20260828_policy_provenance_trace.sql), [상품 근거 추적](../migrations/20260909_chatbot_log_product_trace.sql)의 필요한 부분을 적용한다. 누락 열은 `response_id`, `external_ai_used`, `external_ai_services`, `policy_version`, `applied_rule_ids`, `source_ids`, `response_product_label_trace`다. 부분 적용된 DB에 전체 SQL을 중복 실행하지 않는다.
2. **DB·배포 담당자:** 상품 출처 계보 필드·실제 출처 레지스트리, TLS CA·서비스 토큰·요청 제한·공유 재전송 방지 설정을 준비한다. 현재 로컬 값을 production으로 검사하면 이 항목들이 충족되지 않는다. 대화 저장을 켜려면 [대화 테이블](../migrations/20260828_conversation_history.sql)과 사용자 식별 서명도 준비한다. 현재 실제 MySQL의 대화 저장 설정은 OFF이고 스키마도 부족하다.
3. **프론트·백엔드 담당자:** 실제 AI 주소, ON 프로필 목록, 요청별 동의·사용자 서명, 구조화된 대화 상태, `recipe` 표시, 응답 제한 시간을 연결한다. 현재 프론트의 4초 제한은 이번 생성 응답보다 짧다. 해당 폴더는 수정하지 않았다.

자료 추가는 실제 질문에서 드러나는 근거 범위를 기준으로 진행한다. 이번 변경은 기존 40개 검토 자료의 연결과 문맥 처리를 보강한 것이며, 임상 지식이나 새로운 섭취 판정 범위를 추가한 작업이 아니다.

종합 기록은 `results/priority2_verification.json`, 개별 원문은 `priority2_extended_final.json`, `priority2_live_final.json`, `priority2_live_reviewed.json`, `priority2_mysql.json`, `priority2_server_live.json`, `priority2_actual_startup.json`, 전체 검사 로그는 `priority2_pytest.txt`다. `results/`는 Git 제외 경로이며 이 문서와 재현 코드는 Git에 올릴 수 있다. 최종 전체 검사 전에 나온 회귀 실패도 임시 실행 로그에 남겼고, 수정 전 결과는 덮어쓰지 않았다.

프론트·백엔드·`.env`·실제 DB는 변경하지 않았다. 임시 SQLite 검증은 실제 MySQL 저장이나 AWS·모바일 연동 성공을 뜻하지 않는다. 파일 해시 비교와 Python 구문 검사, `git diff --check`로 수정 범위·파일 상태도 확인했다.
